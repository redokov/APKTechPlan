# TEST-04 — дизайн-записка реализации (2026-11-15, этап 6)

Задача: прод-контур проверки в 1С — подготовка стабильных данных и запуск
сценариев Vanessa Automation переносятся из Python в обработки на встроенном
языке. Authorization: требование владельца 2026-11-14 (см. §10
test02-design-2026-11-14.md), промт продолжения
docs/review/continue-prompt-test04-2026-11-15.md.

## 1. Требование владельца

«Вся питон-обвязка — только этап разработки. В прод идут лишь обработки на
встроенном языке: подготовка данных и запуск тестов / Vanessa». Практический
критерий: ни одна прод-операция проверки не должна требовать вызова `.py`;
Python остаётся для загрузки расширения, команд дизайнера-агента, сравнения
выгрузок, статических проверок и headless-запусков тех же самых точек входа 1С.

## 3. Тх_ПодготовкаТестовыхДанных — стабильный набор

`ПодготовитьСтабильныеДанные()` возвращает `Структура(Создано, Найдено,
Работа, Модели, ТС)`, где `Создано`/`Найдено` — массивы описаний, `Модели` —
структура с ключами `Базовая`/`Аналог`/`БезМощности`, `ТС` — массив ссылок.

Состав набора (фиксированные имена, на них опираются сценарии 01–09):

| Объект | Идентификация | Значимые реквизиты |
|---|---|---|
| вид работы | наименование `Тх_Тест Работа` | — |
| модель `Тх_Тест Базовая` | наименование | `МощностьДвигателя = 100` |
| модель `Тх_Тест Аналог` | наименование | `МощностьДвигателя = 125` (замещение 100/125 = 0,8) |
| модель `Тх_Тест БезМощности` | наименование | реквизит не заполняется — автоподбор обязан её пропустить и назвать в сообщении |
| 4 ТС `Тх_Тест ТС 001..004` | код `ТХТС00001..ТХТС00004` | `АпкМодель = Базовая`, `АпкТипТС = Перечисления.АпкТипыТС.СХТехника`, `АпкХозНомер = ТХХ-0000N` |

Идемпотентность. Модели и работа ищутся по наименованию, ТС — одним запросом
по массиву кодов (`НайтиПоКодам` -> `Соответствие` код/ссылка). Реквизиты
создания применяются ТОЛЬКО при создании: существующий элемент не
перезаписывается, чтобы ручная правка в тестах не откатывалась молча.
Исключение — `ДозаполнитьТС`: у найденного ТС заполняются только ПУСТЫЕ
`АпкМодель` / `АпкТипТС` (SRV-02: тип строки пула берётся из `АпкТипТС`,
без него ТС не попадает в пул).

Стабильный набор НЕ регистрируется в `Тх_РеестрТестовыхОбъектов` и не
подпадает под уборку по маскам: `УбратьОстаткиПоМаскам` исключает его явным
списком имён (иначе sweep `Тх_Тест%` удалит фикстуры между прогонами —
коллизия масок, найденная живым прогоном в TEST-02).

## 4. Тх_ЗапускVanessa — запуск сценария

### 4.1. Контракт `ВыполнитьСценарий(Параметры)`

`Параметры` — `Структура`, читаемые ключи: `КаталогФич` (полный путь к
`.feature`), `ПутьКVanessaAutomation` (epf), `ПутьКТонкогоКлиента` (`1cv8c.exe`),
`СтрокаБазы` (`кластер\база`), `ИмяПользователя` (сеанс TestManager),
`КаталогЛогов`, `КаталогПоиска1cv8` (каталог установки платформы; без него
Vanessa не найдёт версию для тест-клиента — исключение), опционально
`ИмяПользователяТестКлиента` (по умолчанию = `ИмяПользователя`),
`ПортТестКлиента` (`"1538"`), `ВерсияПлатформы` (`"8.5.4"`).

Возврат — `Структура(Вердикт, Источник, Описание, ОшибкаОчистки)`:
`Вердикт` ∈ `PASS`/`FAIL`/`UNKNOWN`, `Источник` ∈ `status-artifact` /
`1c-log` / `conflict` / `none` / `cleanup`, `Описание` — первая содержательная
строка журнала или причина, `ОшибкаОчистки` — `""` либо причина сбоя
гарантированного блока.

Порядок работы: (1) снимок ролей и их назначение; (2) удаление артефактов
прошлого прогона; (3) `vap_<фича>.json` + командная строка + `ЗапуститьПриложение`
с ожиданием; (4) строгий разбор вердикта; (5) гарантированный блок.

Артефакты прогона в `КаталогЛогов` (имя фичи = имя `.feature` без расширения):

| Файл | Назначение |
|---|---|
| `va_exec_<фича>.txt` | лог выполнения сценариев (Vanessa `ДелатьЛогВыполненияСценариевВТекстовыйФайл`) |
| `va_status_<фича>.log` | машинный файл статуса (`0` = ошибок нет) |
| `va_1c_<фича>.log` | журнал тонкого клиента (`/Out`) |
| `vap_<фича>.json` | VAParams, переданные в TestManager |

### 4.2. VAParams

Собираются кодом и пишутся `ЗаписьJSON`/`ЗаписатьJSON` — тот же рецепт, что
в Python-раннере: `ИмяСборки`, `ВерсияПлатформы`, `КаталогПоискаВерсииПлатформы`,
`СтрокаПодключенияКБазе`, `ПутьКVanessaAutomation`, `КаталогФич`,
`КаталогиБиблиотек` (пустой массив), `КлиентыТестирования` (один тонкий клиент
`Основной`, `ПортЗапускаТестКлиента`, `/DisableStartupMessages /DisableStartupDialogs`),
`ВыполнитьСценарии`, `ЗавершитьРаботуСистемы`, `ЗакрытьTestClientПослеЗапускаСценариев`,
`ДелатьЛогВыполненияСценариевВТекстовыйФайл`, `ИмяФайлаЛогВыполненияСценариев`,
`ВыгружатьСтатусВыполненияСценариевВФайл`, `ПутьКФайлуДляВыгрузкиСтатусаВыполненияСценариев`,
`ТаймаутЗапуска1С = 600`. Булевы значения передаются СТРОКАМИ `"Истина"` — так
ожидает Vanessa. Пути к фичам и к epf нормализуются в прямые слэши.

### 4.3. Командная строка TestManager

`<1cv8c> ENTERPRISE /TESTMANAGER /S"<база>" /N"<пользователь>" /P"" /Execute"<epf>"
/CStartFeaturePlayer;VAParams=<json> /DisableStartupDialogs /DisableStartupMessages
/Out"<лог>"`. Ключи с путями — glued (`/Execute"…"`, `/Out"…"`): при раздельном
написании платформа режет путь по пробелу (`C:\Program`) и TestManager висит с
модальным окном, внешне неотличимо от «сценарий выполняется».

### 4.4. Строгий вердикт (fail-closed)

Два независимых артефакта, оба разбираются текстом:

* `va_status_<фича>.log` — после снятия BOM/пробелов/переводов строк содержимое
  должно состоять ТОЛЬКО из цифр; `"0"` -> `PASS`, любое другое число -> `FAIL`,
  всё остальное (в т.ч. пустой файл, который `ЧтениеТекста.Прочитать()` отдаёт
  как `Неопределено`) -> «неизвестно»;
* `va_1c_<фича>.log` — строка должна ЗАКАНЧИВАТЬСЯ предложением Vanessa
  «Выполнение сценариев закончено. Ошибок не было» (`PASS`) либо
  «…БЫЛИ ОШИБКИ» (`FAIL`); завершающая точка необязательна; несколько
  разнородных строк -> «неизвестно».

Сведение: оба известны и расходятся -> `UNKNOWN`/`conflict`; известен один ->
он и берётся (`status-artifact` приоритетнее `1c-log`); неизвестны оба ->
`UNKNOWN`/`none` с первой содержательной строкой журнала. Успех никогда не
выводится из кода возврата процесса — TestManager выходит с 0 и при падении
сценария.

### 4.5. Гарантированный блок

Выполняется всегда (возвратов из `Попытка` выше нет): восстановление точного
состава ролей Тх_ по снимку и `Тх_Тесты.УбратьОстаткиПоМаскам()`. Любая
причина сбоя накапливается в `ОшибкаОчистки`; если очистка не подтвердилась, а
вердикт был `PASS`, он понижается до `FAIL` с `Источник = "cleanup"` — сбой
уборки не может выглядеть успехом (TEST-02, Q-006).

## 5. API ролей

`ИменаРолейТх()` — фиксированный перечень границы TEST-02: `Тх_Чтение`,
`Тх_Редактирование`. `СписокРолейТх(ИмяПользователя)` возвращает массив
назначенных ролей Тх_ или `Неопределено`, если пользователь ИБ не найден.
`ДобавитьРолиТх` / `УдалитьРолиТх` меняют состав через
`ПользователиИнформационнойБазы.НайтиПоИмени` + `Роли.Добавить/Удалить` +
`Записать()` и затем ПЕРЕЧИТЫВАЮТ пользователя, сверяя фактический состав
(«доверяй, но проверяй»); `Ложь` означает «не подтвердилось».
`ВосстановитьРолиТх` из снимка сначала добавляет недостающие, затем снимает
лишние и делает финальную сверку по количеству. Роли вне перечня Тх_ не
трогаются — чужая роль не пересекает границу.

Оркестровка включается только когда сеанс тест-клиента идёт под тем же
пользователем, что и TestManager (`ИмяПользователяТестКлиента` не задан или
совпадает): иначе снимок/восстановление относились бы к другому пользователю.

## 8. Ограничения и вне области

* TestManager и TestClient — один процесс `1cv8c` (`vanessa-automation-single.epf`),
  поэтому «два клиента в одном процессе» — норма, а не сбой.
* Обработки зависят от машины: пути к `1cv8c.exe`, к epf, к каталогу установки
  платформы и версия платформы передаются параметрами, а не берутся из окружения.
* Параметры передаются `Структурой`, без типизированного объекта — валидация
  обязательных ключей выполняется кодом (исключение с понятным текстом).
* Прод-контур не заменяет Vanessa и не содержит бизнес-логики: только сборка
  VAParams, запуск, вердикт и уборка.
* Python-инструменты (`load_extension.py`, `designer_agent*`, `compare_dump_dirs.py`,
  `pre_load_validate.py`, `run_unit_tests_com.py`) остаются в разработке по
  требованию владельца и в поставку не входят.

## 10. Тестовые объекты и поставка (решение владельца 15.11.2026 по TEST-03)

Задача TEST-03 («вынести проверочный код в отдельное расширение») была
запущена в работу и **уперлась в ограничение платформы**, которое проверено
прогонами, а не рассуждением.

### 10.1. Что проверено

1. **Код одного расширения видит объекты другого.** Пробное расширение
   `ТестЗависимости` с общим модулем, обращающимся к `Тх_ТехникаСервер`
   (объект рабочего расширения), загрузилось, применилось и прошло проверку
   модулей без объявления каких-либо зависимостей. То есть сама по себе
   ссылка между расширениями в 8.5.4 работает.
2. **Внешнее соединение видит объекты только одного расширения.** Рабочее
   расширение разделили на два (`ПланированиеТехникиАПК` без проверочных
   объектов и `Тх_ТестоваяОбвязка` с ними). После применения обоих:
   `Обработки.Тх_РаннерТестов`, `Обработки.Тх_ЗапускVanessa`,
   `Константы.Тх_ТестоваяБаза`, `РегистрыСведений.Тх_РеестрТестовыхОбъектов`
   через внешнее соединение **не находятся**, а объекты рабочего расширения
   находятся. Параметры строки соединения (`extension=`, `Ext=`,
   `ExtensionName=`) платформа молча игнорирует - выбрать расширение нельзя.
   Запросы при этом видят объекты обоих расширений (ограничение касается
   только перечислимых коллекций внешнего соединения).

### 10.2. Следствие

На внешнем соединении держится вся автоматизация проверок: запускатор
тридцати одного теста, установка маркера тестовой базы, уборка остатков.
При выносе проверочных объектов во второе расширение эти входы перестают
находиться по имени, то есть **разделение расширений ломает собственный
контур проверки**. Обходные пути (тонкий запускатор в рабочем расширении)
возвращают проверочный код в поставку - то есть отменяют смысл задачи.

### 10.3. Принятый механизм: поставочный профиль

Решение: расширение остаётся одно, а поставка собирается отдельным профилем.
`scripts/make_prod_cfe.py` копирует рабочее дерево в `dist/ПланированиеТехникиАПК`
и убирает из состава и с диска шесть проверочных объектов:

* общий модуль `Тх_Тесты`;
* константа `Тх_ТестоваяБаза`;
* регистр сведений `Тх_РеестрТестовыхОбъектов`;
* обработки `Тх_РаннерТестов`, `Тх_ПодготовкаТестовыхДанных`, `Тх_ЗапускVanessa`.

Содержимое файлов не меняется - только состав, поэтому профиль не может
разойтись с рабочим деревом: `--check` проверяет это побайтно и падает при
любом расхождении, кроме самого перечня объектов. В промышленную базу
ставится профиль из `dist/`, проверочные объекты туда не попадают.

### 10.4. Что это значит для приёмки TEST-03

Требование владельца «проверочный код не должен ехать в промышленную
поставку» выполнено: в поставочном профиле его нет, и это проверяемо
(скрипт + проверка состава). Требование «отдельное расширение» невыполнимо
на этой платформе без потери автоматизации - ограничение зафиксировано
здесь и в книге задач.
