## КЛЮЧЕВОЕ: задача SRV-01 (решения владельца 09.11, night.log строки 323/326)

### Q-001 → вариант B: overlap-interval cleanup

- Удаляется КАЖДАЯ строка регистра Тх_ДефицитТехники, чей период пересекается с запрошенным
  диапазоном хотя бы одним днём (ПериодНачала/ПериодОкончания строки ∩ [ДатаНачала; ДатаОкончания] ≠ ∅).
- Отбор потребности — тем же правилом пересечения (сейчас: `ПериодОкончания >= ДатаНачала И
  ПериодНачала <= ДатаОкончания` — сверить, оно уже пересечённое; ВАЖНО чтобы очистка и отбор
  потребности использовали ОДНО правило — это и есть ядро дефекта P0-2).
- Текущее состояние дефекта: `УстановитьОтборыЗапуска` (Module.bsl ~:1711) ставит ТОЛЬКО
  измерения (сценарий/организация/подразделение/вид) — НЕТ отбора по периоду; очистка
  `НаборЗаписей.Записать(Истина)` стирает ВСЕ строки отборов запуска независимо от периода.
  Комментарий «строки вне запрошенного периода не трогаются» — ложь в коде, это и чиним.
- ТЕХНИЧЕСКАЯ ЗАГОЛОВКА: регистр непериодический (ПериодНачала/ПериодОкончания — измерения,
  не стандартный Период) → `НаборЗаписей.Отбор` НЕ умеет row-level условие пересечения.
  Правильный путь: delete-set = запрос (ключи 10 измерений пересекающихся строк) → удаление
  перечислением ключей (пустой набор с полно-ключевым отбором на каждую группу ключей), либо
  иной канон 8.5 — свериться с MCP `bsl-platform-context` и навыком transactions-locks ДО
  написания кода. Регистр трогать НЕЛЬЗЯ (превращать в периодический — вне полномочий).
- Нерегрессия: строки ВНЕ диапазона (например, мартовские при расчёте января) обязаны остаться.
  Сценарий январь/февраль из решения: расчёт января не должен трогать февральские строки и
  наоборот; добавить юнит-тест + VA-сценарий.

### Q-004 → схема C1: конкурентность

- ВСЕ чтения (потребность, доступность, delete-set) — ВНУТРИ транзакции, ПОСЛЕ взятия блокировки.
- Блокировка — ТОЧНЫЙ набор ключей: `ЭлементБлокировкиДанных.ИсточникДанных` +
  `ИспользоватьИзИсточникаДанных` (принимает РезультатЗапроса — API проверено через
  bsl-platform-context при решении Q-004); источник данных = delete-set (пересекающиеся строки)
  + ключи записываемых строк. НЕ поштучное `УстановитьЗначение` по измерениям (текущая
  реализация ~:1486-1512 — грубая блокировка по измерениям, её ЗАМЕНЯЕМ).
- Ожидание блокировки ОГРАНИЧЕНО: по истечении — полный откат, явное сообщение пользователю,
  БЕЗ автоповтора (владелец перезапускает вручную).
- Документы планов НЕ блокируются (остаточный риск принят, корректируется следующим расчётом).
- Implementation note из решения: delete-set ПЕРЕЗАПРАСИТЬ после взятия блокировки
  (между первым чтением и блокировкой могли появиться новые строки).
- Финальная запись — как сейчас (атомарность и запись результатов вне дефектного скоупа не менять).
- Параллельный прогон: два одновременных расчёта одного скоупа → ровно один консистентный
  результат, проигравший получает bounded-wait сообщение. Юнит-тест параллельности в COM
  невозможен (одна сессия) → обосновать выбранную форму проверки (например, два фоновых
  задания в одной сессии сервера через Тх_Тесты-хелпер, либо VA-сценарий с двумя расчётами
  и инвариантом результата). Если форма требует GUI/фоновых заданий, недоступных headless —
  зафиксировать ограничение и согласовать с владельцем, НЕ имитировать.
