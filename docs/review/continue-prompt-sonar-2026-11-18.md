### 1. Про VPN — ключевое препятствие

Серверы Jenkins (`https://192.168.200.52:8443`) и SonarQube
(`http://192.168.200.52:9090`) сидят за VPN. **VPN был недоступен на протяжении
всей ночной сессии**: каждое наблюдение с 2026-11-17 ~19:00 по 2026-11-18 10:22
давало код доступа 000 (нет маршрута) у обоих серверов. Момент, когда VPN
«отвалился», неизвестен — к началу ночной сессии он уже был вниз. Четыре фоновых
наблюдателя опрашивали достижимость всю ночь (каждые ~2 мин), ни одного
положительного ответа.

**Первое же действие в новой сессии — проверь VPN сам** (локально, дёшево):

```bash
curl -s -m 8 -o /dev/null -w "jenkins -> %{http_code}\n" https://192.168.200.52:8443
curl -s -m 8 -o /dev/null -w "sonar  -> %{http_code}\n" http://192.168.200.52:9090
```

- **VPN поднялся** (оба кода не 000; 200/302/401/403 — все годятся) → выполняй §2.
- **VPN вниз** → запусти фонового наблюдателя (субагент, `run_in_background`,
  модель `wormsoft/zai/glm-5.3:NVFP4`, `max_turns: 150`) с алгоритмом:
  каждый ход — curl-проверка обоих серверов; оба не-000 → `sleep 30`, перепроверка,
  при успехе вернуть `RESULT: VPN_UP` + оба кода и завершиться; иначе `sleep 110`
  и повтор; при исчерпании лимита — `RESULT: VPN_STILL_DOWN`. Наблюдатель —
  строго только для чтения: никаких вызовов Jenkins/Sonar API, никаких изменений.
  Учти: окно тарификации API сбрасывается каждые ~2 часа, и в момент сброса
  фоновые субагенты погибают («This operation was aborted») — после каждого
  возобновления сессии перезапускай наблюдателя заново (это нормальный цикл,
  взвод автопродолжения: `python C:/Tools/pi-billing-window/scripts/arm_cont_after_reset.py
  "$PI_SESSION_FILE" --repeat 5 --ttl 20`).
