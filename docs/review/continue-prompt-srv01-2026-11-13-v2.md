## РАЗРЕШЕНИЕ ПРОТИВОРЕЧИЯ C1 (принято в сессии 7, вариант A — НЕ ре-литигировать)

Противоречие: точная блокировка (delete-set + write-keys) требует чтений ДО
блокировки, а C1 требует всех чтений ПОСЛЕ. Разрешение (единственное,
совместимое с припиской самого владельца «delete-set ПЕРЕЗАПРАСИТЬ после
блокировки», которая неявно допускает чтение-до для построения области):

1. Чтения-до-блокировки (потребность №1 + delete-set №1) — ТОЛЬКО для состава
   ТЗ источника блокировки.
2. Блокировка точным набором (F2-F5), маппинг по 8 измерениям БЕЗ
   Источник* — строки перемещений (любой источник) покрыты ключом спроса.
3. После блокировки — авторитетные чтения: потребность №2, доступность
   (SRV-02-контракт, ДатаСреза = сырой параметр ДатаНачала или Неопределено,
   НЕ дефолт 0001-01-01!), delete-set №2 (перезапрос).
4. **Страж области**: наборы ключей (КлючЗаписиДефицита) потребности №1/№2 и
   delete-set №1/№2 сравниваются; расхождение = параллельное изменение →
   полный откат + сообщение, БЕЗ автоповтора. Закрывает дыру «строки созданы
   между чтением-до и блокировкой».
5. Удаление перечислением ключей (F1), запись как раньше (Записать(Ложь)).

**ПЕРВЫЙ ШАГ НОВОЙ СЕССИИ: дополнить дизайн-записку §5** этим разрешением
(двойное чтение потребности + страж) — сейчас в §5 потребность читается один
раз до блокировки, без стража. Затем реализация.
