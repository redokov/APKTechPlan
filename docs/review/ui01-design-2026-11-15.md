# UI-01 дизайн-записка: пометка устаревания расчёта (Q-008 вариант c)

Дата: 2026-11-15. Задача: UI-01 (spec-003), этап 4 night-run.
Предыдущая запись: §7.3 tasks.md (частичная поставка 2026-11-14, коммит 769efc2).

## 1. Решение по механизму обнаружения (вопрос владельца из промта)

Платформенного механизма дат изменения записей в доступном контексте нет
(проверено ранее: `ДатыИзменения`, `ОбновитьДатыИзменения` не найдены; у
регистров накопления нет даты изменения записи). По умолчанию (промт
2026-11-14, «работу не блокирует») принят вариант (а):

**Признак изменения = самая поздняя дата регистратора (поле `Период`) в
регистрах годового плана `АпкМеханизированныеРаботыПоГодовомуПлану` и
`АпкТранспортныеРаботыПоГодовомуПлану` по сценарию новее сохранённого
момента расчёта.**

Ограничение (зафиксировано честно): правка документа-регистратора БЕЗ
изменения его даты не обнаруживается — период записи регистра равен дате
документа. Альтернативы для владельца: (б) тот же признак + контроль
количества строк потребности; (в) отпечаток (количество + контрольная
сумма строк) — дороже, ловит любые правки. Ни одна не реализована без
решения владельца.

## 2. Реализация

- **Регистр `Тх_МоментРасчета`** (РС, непериодический): измерение
  `СценарийПланирования` (главное, запрет пустых), ресурс
  `МоментРасчета`. Тип ресурса исправлен с `Date` на `DateTime` на этом
  этапе: только-дата обрезала бы время расчёта и давала ложную пометку
  «устарело» для источников того же дня.
- **`Тх_ТехникаСервер`**: `ЗаписатьМоментРасчета` (закрытая) вызывается
  строго перед `ЗафиксироватьТранзакцию()` внутри `РассчитатьДефицит` —
  момент и строки дефицита пишутся одной транзакцией (либо всё, либо
  ничего). Публичные: `МоментРасчетаДефицита(Сценарий)` (нет расчёта =
  `00010101`), `ДанныеРасчетаУстарели(Сценарий)` → структура
  `Устарели/МоментРасчета/ПоследнееИзменение`; запрос к источникам
  обёрнут в Попытку (недоступность модуля АПК/прав не роняет открытие
  формы, причина — в ЖР, уровень Предупреждение — осознанно: это не
  ошибка операции).
- **Форма `Тх_РасчетДефицита`**: реквизит `ПометкаУстаревания` (Строка),
  элемент-декорация `ПометкаУстаревания` (LabelDecoration, заголовок
  заполняется кодом, пустой текст скрывает элемент). Заполнение в
  `ПриСозданииНаСервере` (предзаполненный сценарий), пересчёт в
  `СценарийПланированияПриИзменении` (событие добавлено в Form.xml,
  порядок OnChange/StartChoice = канон платформы) и снятие после
  успешного расчёта в `РассчитатьИОткрытьОтчет`. Текст: «Данные расчёта
  устарели: источники изменялись <дата>. Выполните расчёт повторно.»
- **Тест-обвязка**: `ВосстановитьДефицитПоСценарию` в `Тх_Тесты` теперь
  чистит и запись момента (вместе со строками дефицита), иначе после
  удаления тестового сценария в регистре оставалась бы висячая ссылка.
  Прогон юнитов 30/30 (включая `ЧистотаТестовыхДанных`) — чистота
  подтверждена.

## 3. Текст «нет данных» в СКД (Q-008 вариант b) — РЕШЕНО 15.11.2026 программно

Элемент `dcsset:noDataText`, добавленный в вариант настроек схемы
(коммит 769efc2), платформа 8.5.4 ОТВЕРГАЕТ на загрузке:
`Исключение XDTO произошло при чтении файла …ОсновнаяСхемаКомпоновкиДанных\Ext\Template.xml`
— правка исходников XML блокирует ВСЮ загрузку расширения (два прогона
load_rc=1, воспроизводимо). Элемент удалён из исходников (файл вернул к
состоянию ccfb5fa), чтобы разблокировать поставку.

Выводы для владельца:
- вариант b в этой редакции НЕ реализуем правкой XML-исходников —
  платформа не принимает `dcsset:noDataText` внутри `settingsVariant`
  сериализации СКД 8.5;
- `pre_load_validate.py` этот режим XDTO не ловит (27 файлов OK при
  нерабочем файле) — известное ограничение гейта;
- альтернативы: задать текст в Конфигураторе интерактивно и проверить
  контрольной выгрузкой фактический синтаксис, либо установить текст
  программно при компоновке отчёта. Без проверки фактической
  сериализации новый синтаксис не выдумывать (запрет промта).

Текущее поведение пользователя: отчёт с нулём строк открывается со
стандартным «нет данных» платформы; в форме расчёта есть своё
информационное сообщение «Данные для отчёта не рассчитаны…» (было
раньше, сохранено).

### 3.1. Решение владельца 15.11.2026 и реализация

Владелец выбрал вариант «программно» (В2): текст выводится кодом отчёта, а не
настройкой схемы компоновки. Реализовано в модуле объекта отчёта
`Отчёты/Тх_ДефицитТехники/Ext/ObjectModule.bsl`:

* обработчик `ПриКомпоновкеРезультата` выполняет компоновку сам
  (схема -> настройки -> макет -> процессор -> вывод в документ), потому что
  дописать строку после штатного вывода нельзя;
* пустота результата определяется до вывода: у процессора компоновки
  вызывается `Следующий()`, `Неопределено` означает «записей нет»;
* при пустом результате вызывается `ВывестиТекстОтсутствияДанных`, которая
  пишет в тело отчёта строку «Данных нет» (жирным, 12 пунктов);
* вся ручная компоновка обёрнута в `Попытка`: при любом сбое управление
  возвращается платформе (`СтандартнаяОбработка = Истина`), то есть отчёт
  не может перестать открываться из-за этого механизма.

Проверка: новый тест `ТестТекстОтсутствияДанных` (в наборе стало 31 проверка)
проверяет две вещи - что механизм пишет текст в пустой документ и что на
реальной схеме отчёта отбор с заведомо недостижимой границей периода даёт
пустой результат. Обычный путь (отчёт с данными) проверяется сценарием
проверки 06 в общем прогоне.

Грабли, пойманные при реализации (8.5.4, линтер их не видит):

* `КомпоновщикМакетаКомпоновкиДанных.Скомпоновать` в 8.5 называется
  `Выполнить` и принимает только схему и настройки: передача расшифровки
  четвёртым параметром даёт «Несоответствие типов (параметр номер '4')»;
* отбор схемы компоновки с ПУСТЫМ правым значением платформа трактует как
  «отбор не задан» и пропускает - для проверки пустого результата нужна
  заведомо недостижимая граница (в тесте: период с 01.01.2100).
