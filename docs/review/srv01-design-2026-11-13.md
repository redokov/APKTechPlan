## 1. Исходные решения (владелец, night.log 09.11)

- **Q-001 → B**: удаляется КАЖДАЯ строка Тх_ДефицитТехники, чей период
  пересекается с запрошенным диапазоном хотя бы одним днём. Отбор потребности —
  тем же правилом. Регистр НЕ переводится в периодический (вне полномочий).
  Нерегрессия: строки вне диапазона обязаны остаться (январь/февраль).
- **Q-004 → C1**: все чтения внутри транзакции ПОСЛЕ блокировки; блокировка —
  точный набор ключей (delete-set + ключи записываемых строк) через
  ИсточникДанных; НЕ поштучное УстановитьЗначение по измерениям (текущая
  грубая схема :1491-1506 заменяется). Ожидание блокировки ограничено: по
  истечении — полный откат, явное сообщение, БЕЗ автоповтора. Документы планов
  не блокируем (остаточный риск принят). Delete-set ПЕРЕЗАПРАШИВАЕТСЯ после
  взятия блокировки. Финальная запись — как сейчас (Записать(Ложь)).

### 2.2 Выводы для дизайна

1. **Bounded-wait**: в 8.5.4.1683 НЕТ параметра-таймаута `НачатьТранзакцию`
   (8.3-форма удалена, F7) и НЕТ per-call управления ожиданием блокировки (F6).
   Единственный механизм — сеансовая настройка ИБ «ВремяОжиданияБлокировкиДанных»
   (дефолт 20 сек, F9): `Заблокировать()` ждёт максимум её значение, затем
   выбрасывает исключение. Это удовлетворяет C1 поведенчески: по истечении —
   исключение → полный откат → явное сообщение → без автоповтора.
   **OWNER-REVIEW флаг №5**: bounded-wait реализован настройкой ИБ (в тестовой
   базе дефолт 20 сек, мы её НЕ меняем); per-call таймаут в 8.5 недоступен;
   `УстановитьВремяОжиданияБлокировкиДанных` требует ИБ без других сеансов и для
   прод-кодa непригоден (админ-действие при развёртывании — опционально).
   Точный текст исключения по таймауту будет зафиксирован юнит-тестом
   параллельности (§6), т.к. воспроизвести конфликт в одном COM-сеансе нельзя (F11).
2. **Форма проверки параллельности**: два COM-сеанса НЕ годятся (F11).
   Фоновые задания из серверного сеанса ПРИГОДНЫ — доказано пробами
   2026-11-13 (прогоны 9-10, зонд ред.3): `ФоновыеЗадания.Выполнить`
   возвращает объект «Фоновое задание»; API 8.5 отличается от 8.3:
   - `Идентификатор` НЕ существует → `УникальныйИдентификатор` (UUID);
   - есть `ИмяМетода`, `Наименование`, `Состояние` (строка «Задание
     выполняется»);
   - `ВремяНачала`/`ВремяКонца`/`ИдентификаторЗадания` НЕ существуют;
   - `ОжидатьЗавершения(<Сек>)` — ПРОЦЕДУРА (вызов как функции —
     «Обращение к процедуре объекта как к функции»);
   - перечисление `СостояниеФоновогоЗадания.Выполняется` НЕ доступно
     (результат-«Поле объекта не обнаружено» при runtime-компиляции).
   Форма параллельности — юнит-тест `ТестОжиданиеБлокировкиОграничено`:
   ФЗ-«победитель» (экспортный хелпер `ДержатьБлокировкуДефицита`)
   держит блокировку области, тест вызывает `РассчитатьДефицит` и
   проверяет исключение/откат/ограниченность ожидания. Флаг №4 закрыт
   реализацией (ограничение «два COM-сеанса» снято ФЗ).
3. **Блокировка**: реализация на F2–F5 (Область + ИсточникДанных-ТЗ + маппинг),
   никаких поштучных УстановитьЗначение по измерениям.

## 3. Правило пересечения (ядро P0-2)

Строка регистра входит в delete-set ⟺

```
Строка.ПериодОкончания >= ДатаНачала  И  Строка.ПериодНачала <= ДатаОкончания
```

— символьно ТО ЖЕ условие, что и отбор потребности в `ЗапросПотребности`
(:577-580). Дефолты дат запуска: `Дата(1,1,1)` / `Дата(3999,12,31)` — как в
`ЗапросПотребности` (:570-571). Одно правило для очистки и отбора — требование
P0-2 (сейчас комментарий :1480-1483 «строки вне периода не трогаются» лжёт:
`Записать(Истина)` по отборам запуска стирает все периоды).

**Кейс пустых дат запуска** (осознанный, без отдельной ветки): при пустых
ДатаНачала/ДатаОкончания пересечение = ВСЕ строки сценария → очистка = полная
перезапись по остальным отборам; консистентно с отбором потребности (тоже все).
Документировано, поведение не ветвится.

Отборы запуска поверх пересечения: СценарийПланирования — всегда; Организация /
Подразделение / ВидТехники — если заполнены (как `УстановитьОтборыЗапуска` :1711,
семантика сохраняется: расчёт одного вида техники не трогает строки других видов).

## 4. Канон удаления (подтверждён F1)

`ПериодНачала`/`ПериодОкончания` — ИЗМЕРЕРИЯ регистра (не стандартный Период) →
пересечение на уровне строк НЕ выражается отбором набора записей. Канон:

1. Запрос delete-set: 10 измерений всех строк регистра под отборами запуска И
   условием пересечения (запрос №1).
2. Блокировка (см. §5).
3. ПЕРЕЗАПРОС delete-set после блокировки (решение владельца; запрос №2 —
   тот же текст).
4. Цикл по строкам delete-set: `НаборЗаписей` с полно-ключевым отбором по 10
   измерениям → `Записать(Истина)` (пустой набор) — удаляет ровно одну строку.
   Демо-объём: 46 строк — 46 коротких записей, приемлемо (NFR не нарушается).
5. Запись новых строк: набор с отборами запуска (`УстановитьОтборыЗапуска`),
   `Загрузить`/`Добавить` строк, `Записать(Ложь)` — добавление БЕЗ очистки.
   Строки вне диапазона физически не перезаписываются → нет лишних DBMS-блокировок
   и нет конфликтов с параллельным расчётом другого периода (ядро C1).

Альтернатива «выгрузить остаток + новые, Записать(Истина) по отборам запуска»
ОТКЛОНЕНА: физически переписывает строки вне диапазона (идентичные значения, но
delete+insert) → лишние блокировки и ложные конфликты параллельных расчётов,
противоречит «вне диапазона не трогать».

Нерегрессия периодов гарантирована конструкцией: вне диапазона не попадают ни в
delete-set, ни в набор записи. Детерминизм повторного расчёта (NFR-005): строки
прошлого расчёта того же диапазона пересекаются с ним самим → удаляются →
результат идемпотентен.

## 5. Схема транзакции (C1, вариант A: чтения-до только для области + страж)

**Разрешение противоречия C1** (принято в сессии 7, НЕ ре-литигируется):
точная блокировка через ИсточникДанных требует знать состав ключей ДО
блокировки, а решение C1 требует всех содержательных чтений ПОСЛЕ. Разрешение
опирается на приписку самого владельца «delete-set ПЕРЕЗАПРАСИТЬ после
блокировки», неявно допускающую чтение-до для построения области:

1. Чтения-до-блокировки — ТОЛЬКО для состава ТЗ источника блокировки:
   потребность №1 + delete-set №1; из расчёта НЕ используются.
2. Блокировка точным набором (F2–F5), маппинг по 8 измерениям БЕЗ Источник* —
   строки перемещений (любой источник) покрыты ключом спроса.
3. После блокировки — авторитетные чтения: потребность №2, доступность
   (SRV-02-контракт, ДатаСреза = сырой параметр ДатаНачала или Неопределено,
   НЕ дефолт 0001-01-01), delete-set №2 (перезапрос); ИндексУровня1 строится
   здесь же, из авторитетной таблицы доступности.
4. **Страж области**: наборы ключей (КлючЗаписиДефицита) потребности №1/№2 и
   delete-set №1/№2 сравниваются; расхождение = параллельное изменение между
   чтением-до и блокировкой → полный откат + сообщение, БЕЗ автоповтора.
   Закрывает дыру «строки созданы между чтением-до и блокировкой».
5. Удаление перечислением ключей (F1), запись как раньше (Записать(Ложь)).

Порядок внутри `РассчитатьДефицит` (текущий :1444-1594 перестраивается):

```
1. Валидации (как сейчас, :1446-1460) — до транзакции.
2. НачатьТранзакцию()            // БЕЗ параметра (F7)
   Попытка
3.   Чтение-до №1 (только для области блокировки, в расчёт НЕ идёт):
       потребность №1 (ЗапросПотребности.Выгрузить)
       delete-set №1 (ЗапросКлючейОчистки: 10 измерений, отборы запуска
         + пересечение §3)
4.   ТЗ блокировки = ключи потребности №1 ∪ ключи delete-set №1
       (8 колонок-измерений, БЕЗ Источник*; фильтр вида техники запуска)
5.   Блокировка (F2–F5):
       Элемент = Блокировка.Добавить()
       Элемент.Область      = "РегистрСведений.Тх_ДефицитТехники"
       Элемент.Режим        = Исключительный
       Элемент.ИсточникДанных = ТЗ блокировки
       Для каждого измерения X из 8 (БЕЗ Источник*):
         Элемент.ИспользоватьИзИсточникаДанных(X, X)   // порядок F3
       Блокировка.Заблокировать()      // ждёт ≤ ВремяОжиданияБлокировкиДанных (20 c)
6.   Авторитетные чтения ПОСЛЕ блокировки (ядро C1):
       потребность №2 (тот же запрос)
       доступность (SRV-02-контракт; ДатаСреза = сырой параметр ДатаНачала
         или Неопределено — НЕ дефолт 0001-01-01)
       delete-set №2 (перезапрос, тот же текст запроса)
       ИндексУровня1 = ИндексПрипискиПоОргПодр(ТЗДоступность)
7.   СТРАЖ ОБЛАСТИ: ключи потребности №1 = ключи потребности №2
       И ключи delete-set №1 = ключи delete-set №2
       (КлючЗаписиДефицита; для очистки источники — из полей строки);
       расхождение → исключение → полный откат → сообщение, БЕЗ автоповтора
8.   Цикл удаления по ключам delete-set №2 (канон §4, п.4)
9.   Формирование строк (существующая логика сопоставления, тело цикла НЕ
     меняется; КлючиСтрок-защита) + набор записи с отборами запуска,
     Записать(Ложь)
10.  ЗафиксироватьТранзакцию()
   Исключение
     ОтменитьТранзакцию()
     ВызватьИсключение СтрШаблон(
       НСтр("ru='Расчёт дефицита не выполнен: … Повторите запуск вручную. Причина: %1'"),
       КраткоеПредставлениеОшибки(ИнформацияОбОшибке())) // явное сообщение,
     БЕЗ автоповтора; текст таймаута блокировки уточняется тестом §6
   КонецПопытки
```

Замечания:
- ТЗ блокировки (п.4): строка = кортеж 8 измерений спроса (Источник* НЕ
  маппится — строки перемещений покрыты ключом спроса); источники строк —
  потребность №1 и delete-set №1; дедупликация кортежей — через
  КлючЗаписиДефицита по 8 измерениям (пустые источники).
- Пустые ТЗ блокировки (0 строк: нечего ни удалять, ни писать) — блокировать
  нечего (F5, безопасно); после авторитетных чтений №2 ранний выход без
  записи, если и потребность №2, и delete-set №2 пусты.
- Режим наборов: как сейчас (независимый регистр, управляемые блокировки).
- Документы АпкПланТехническихРесурсов НЕ блокируем (остаточный риск владельца).
- Комментарий-ложь :1480-1483 удаляется/заменяется на описание реального канона.
- Чтения-до №1 и №2 — один и тот же текст запроса; страж (п.7) гарантирует,
  что в расчёт попадает только №2, а №1 использован исключительно областью
  блокировки — противоречие C1 закрыто конструктивно, а не компромиссом.
