# Design: Анализ дефицита техники (по технологическим картам)

> Requirements: @requirements.md
> Status: Approved (ночной автономный прогон по standing-инструкции; ревью утром)
> Last Updated: 2026-10-07
> Gate: requirements:approved подтверждён (.status), все Must Have покрыты ниже.

## 1. Executive Summary

Продукт — **расширение №2 «ПланированиеТехникиАПК»** (CFE, префикс объектов «Тх_»)
к конфигурации «1С:ERP + модуль АПК 2.5», где модуль АПК сам является
расширением №1 («Расширение_АПК»). Ключевое архитектурное ограничение: по
документации платформы расширение может ссылаться типами только на объекты
основной конфигурации, поэтому **все ссылки на объекты расширения №1 (Апк*)
в собственных объектах расширения №2 делаются generic-составными типами**
(`СправочникСсылка` и т.п.) с строковым именем целевого объекта и рантайм-доступом
(запросы с явными именами таблиц, `Справочники["Имя"]`, `Тип("СправочникСсылка.Имя")`
для валидации). Прямые типы допустимы только на core-объекты ERP (Организации,
СтруктураПредприятия, ТранспортныеСредства).

Потребность в сменах берётся **из типовых оборотных регистров годового плана**
(`АпкМеханизированныеРаботыПоГодовомуПлану`, `АпкТранспортныеРаботыПоГодовомуПлану`)
через рантайм-запросы — быстрее чтения ТЧ техкарт и учитывает «КорректировкаРегистров».
Доступность — из нового документа «Тх_ПланТехническихРесурсов» (принятые ТС).
Отчёт — **двухфазная схема**: серверный расчёт заполняет собственный регистр
сведений «Тх_ДефицитТехники», отчёт СКД читает только этот регистр (быстро,
простая СКД, детерминизм). Реализация авторится офлайн (XML+BSL), гейтится
bsl-ls + pre_load_validate; загрузка в базу отложена до подъёма кластера (утро).

### Граница между расширениями (ФАКТ-1)

- Расширение №2 **не заимствует** и не перехватывает объекты расширения №1
  и core-конфигурации (NFR-003). Весь доступ к типовым данным — чтение.
- Объекты core ERP (Организации, СтруктураПредприятия, ТранспортныеСредства) —
  прямые типы `CatalogRef.*`.
- Объекты расширения №1 (ВидыРаботСотрудников, АпкМоделиСХТехники,
  АпкМоделиАвтотранспорта, АпкСценарииПланирования, регистры *ПоГодовомуПлану,
  реквизиты ТС АпкХозНомер/АпкМодель, реквизит МощностьДвигателя) — generic-типы
  + рантайм-доступ (§4.1).
- Если расширение №1 отключено/удалено — рантайм-запросы к его таблицам падают;
  обработки ловят исключение и выдают понятное сообщение (см. §8), объекты
  расширения №2 остаются работоспособными.

### 4.1 Стратегия типов (ФАКТ-1)

Правило: тип реквизита/измерения может быть `CatalogRef.*` / `DocumentRef.*`
только для объектов **основной конфигурации ERP**. Для объектов расширения №1 —
generic-составной тип + строковое имя целевого объекта + рантайм-доступ.
Формы выбора и чтение реквизитов — по строковым именам.

| Реквизит (объект) | Тип в метаданных | Целевой объект (строка) | Конвертация / доступ |
|---|---|---|---|
| Работа (Тх_КоэффициентыПересчетаРабот, Тх_ДефицитТехники) | `СправочникСсылка` (составной, любые справочники) | `ВидыРаботСотрудников` | форма выбора `ОткрытьФорму("Справочник.ВидыРаботСотрудников.ФормаВыбора")`; валидация `ТипЗнч(Значение) = Тип("СправочникСсылка.ВидыРаботСотрудников")` в ПередЗаписью |
| МодельТехники (регистры, документ) | `СправочникСсылка` | `АпкМоделиСХТехники` (вид СХТехника) / `АпкМоделиАвтотранспорта` (вид Автотранспорт) | выбор формы по значению ВидТехники; валидация `Тип(...)` рантайм |
| СценарийПланирования (документ, Тх_ДефицитТехники) | `СправочникСсылка` | `АпкСценарииПланирования` | форма выбора по имени; валидация рантайм |
| Подразделение (документ, Тх_ДефицитТехники) | `CatalogRef.СтруктураПредприятия` | core ERP | прямой тип |
| Организация | `CatalogRef.Организации` | core ERP | прямой тип |
| ТранспортноеСредство (ТЧ документа) | `CatalogRef.ТранспортныеСредства` | core ERP | прямой тип; хоз.номер и модель ТС — реквизиты **расширения №1** (`АпкХозНомер`, `АпкМодель`), читаются рантайм-запросом, типами недоступны |
| МощностьДвигателя (только чтение) | — | реквизит `АпкМоделиСХТехники` | только рантайм-запрос |

Правила рантайм-доступа:
1. Запросы к таблицам расширения №1 — текстом, с явным именем таблицы
   (`АпкМеханизированныеРаботыПоГодовомуПлануОбороты` и т.п.), компиляция
   в рантайме. Обёртка `Тх_ТехникаСервер.ВыполнитьЗапросАПК(Текст, Параметры)`
   ловит исключение и возвращает понятную ошибку «модуль АПК недоступен».
2. Валидация значений generic-полей — `Тип("СправочникСсылка.<Имя>")` в
   рантайме; несовпадение типа → отказ записи с сообщением.
3. Пустое строковое имя целевого объекта хранится в коде модуля
   Тх_ТехникаСервер (константы имён), не в данных.

**Задача верификации (после подъёма кластера):** эмпирически проверить,
допускает ли платформа 8.5 прямые типы на объекты другого расширения
(тестовый реквизит `CatalogRef.АпкМоделиСХТехники`, загрузка через
db-load-xml). Если допускается — точечная замена generic-типов прямыми
(оптимизация, смена не требуется: рантайм-запросы остаются).

### 4.2 Подсистема Тх_ПланированиеТехники

Состав: объекты 2–9 из §4.0. Командный интерфейс:
- Панель навигации: «Планы технических ресурсов» (список документа),
  «Коэффициенты пересчёта работ» (список регистра), «Дефицит техники» (отчёт).
- Панель действий: «План технических ресурсов» (создание),
  «Заполнение коэффициентов», «Расчет дефицита».
- Видимость команд регулируется ролями (§4.9).

### 4.3 Регистр сведений Тх_КоэффициентыПересчетаРабот

Независимый, непериодический. Режим записи: «Независимый» (ведение формой списка).

Измерения:
| Поле | Тип | Примечание |
|---|---|---|
| Период | Дата | «действует с», аналог шапки «Период» референса s02 |
| Работа | СправочникСсылка → ВидыРаботСотрудников | §4.1 |
| МодельТехники | СправочникСсылка → АпкМоделиСХТехники/АпкМоделиАвтотранспорта | |
| ВидТехники | EnumRef.Тх_ВидыТехники | различает каталоги моделей внутри generic-типа |

Ресурсы:
| Поле | Тип | Примечание |
|---|---|---|
| Коэффициент | Число (10,4), неотрицательное | K = смен_аналога / смен_базовой (TD-004) |
| БазоваяМодель | Булево | у базовой K = 1,00 принудительно (FR-003) |

Поведение:
- Дубль «период+работа+модель+вид» невозможен физически (измерения = ключ) — FR-018.
- Модуль набора записей, `ПередЗаписью`: (а) не более одной строки
  `БазоваяМодель = Истина` в наборе на (Работа+Период+ВидТехники);
  (б) у базовой строки Коэффициент принудительно = 1,00;
  (в) валидация типов ссылок (§4.1 п.2).
- Выборка «коэффициент на дату D» — запросом: последняя запись с
  `Период <= D` по (Работа+Модель+ВидТехники); функция
  `Тх_ТехникаСервер.КоэффициентНаДату(...)` возвращает число или `Неопределено`.

Форма списка (`Тх_ФормаСписка`): динамический список по регистру, отбор
по Периоду (реквизит шапки формы, как в s02), колонки
Работа / МодельТехники / Коэффициент / БазоваяМодель; команды создания
и удаления записи. Никаких модальных окон (NFR-001).

### 4.4 Документ Тх_ПланТехническихРесурсов («План технических ресурсов»)

Шапка:
| Поле | Тип | Примечание |
|---|---|---|
| Организация | CatalogRef.Организации | |
| Подразделение | CatalogRef.СтруктураПредприятия | как в техкартах/регистрах АПК (Requirements feedback п.2) |
| СценарийПланирования | СправочникСсылка → АпкСценарииПланирования | §4.1 |
| Комментарий | Строка (0) | |

Три ТЧ — одинаковая структура (ОсновнаяТехника / Оборудование / Автотранспорт;
ВидТехники по ТЧ: СХТехника / Оборудование / Автотранспорт):
| Колонка | Тип | Примечание |
|---|---|---|
| ТранспортноеСредство | CatalogRef.ТранспортныеСредства | обязательная (Q-003: только конкретные ТС) |
| МодельТехники | СправочникСсылка | автозаполнение из АпкМодель ТС рантайм-запросом; редактируемо |
| Принят | Булево, default Истина | FR-007 |
| Количество | Число (5,0), default 1 | для строки «одна единица» = 1 |
| Комментарий | Строка (0) | |

Поведение:
- `ПриИзмененииТранспортногоСредства` (серверный вызов): рантайм-запрос
  `АпкМодель` + `АпкХозНомер` выбранного ТС → заполнить МодельТехники,
  показать хоз.номер (вычисляемая колонка формы «ХозНомер», не сохраняется).
- Проведение: контроль дублей ТС внутри документа; движения не создаём —
  расчёт читает ТЧ запросом `Проведен = ИСТИНА`.
- `ОбработкаПроведения` (неблокирующая проверка): если то же ТС уже «Принято»
  в другом проведённом плане **того же сценария, другого подразделения** —
  предупреждение в сообщения пользователю (не отказ).
- Форма документа: шапка + 3 закладки ТЧ (референс s03/s04), счётчики
  «Принято единиц» по каждой ТЧ в заголовках закладок; форма списка — типовая
  структура, отборы по организации/подразделению/сценарию.

### 4.5 Отчёт Тх_ДефицитТехники (СКД) — двухфазная схема

Фаза 1 (обработка Тх_РасчетДефицита): серверный расчёт (§4.7) очищает и
заполняет регистр Тх_ДефицитТехники по отборам запуска.
Фаза 2 (отчёт): СКД с набором данных «Запрос» **только к Тх_ДефицитТехники** —
без рантайм-запросов к расширению №1 (надёжно, быстро, NFR-002).

Регистр Тх_ДефицитТехники (независимый, непериодический), заполняется
исключительно обработкой:
- Измерения: Организация (CatalogRef.Организации), Подразделение
  (CatalogRef.СтруктураПредприятия), СценарийПланирования (СправочникСсылка),
  ПериодНачала (Дата), ПериодОкончания (Дата), ВидРаботы (СправочникСсылка),
  МодельТехники (СправочникСсылка), ВидТехники (EnumRef.Тх_ВидыТехники).
- Ресурсы: ПотребностьСмен (10,2), ДоступноСмен (10,2), НехватаетСмен (10,2),
  ДнейПериода (5,0), СменВДень (5,1), КоэффициентНеЗадан (Булево),
  ПланТехресурсовОтсутствует (Булево).

Отчёт:
- Группировки (по s05): Подразделение → ДатаНачала (ПериодНачала) →
  ДатаОкончания (ПериодОкончания) → ВидРаботы → МодельТехники.
- Колонки: ПотребностьСмен, ДоступноСмен, «Не хватает смен» (НехватаетСмен),
  ДнейПериода, СменВДень.
- Параметры-отборы (FR-014): Организация, Подразделение, СценарийПланирования,
  Период (с..по), ВидРаботы, МодельТехники, ВидТехники.
- Параметр «ТолькоДефицит» (Булево, default Истина) → отбор `НехватаетСмен > 0` (FR-015).
- Условное оформление: строки с `КоэффициентНеЗадан = Истина` — пометка
  «коэффициент не задан» (FR-011); строки с `ПланТехресурсовОтсутствует = Истина` —
  пометка «план техресурсов отсутствует» (NFR-005, UX Notes: не ноль и не ошибка).

### 4.6 Обработка Тх_ЗаполнениеКоэффициентов («Заполнение коэффициентов по мощности»)

Форма: Работа (generic, выбор из ВидыРаботСотрудников), Период (Дата),
БазоваяМодель (generic, выбор из АпкМоделиСХТехники), кнопка «Заполнить».
Серверная процедура (Тх_ТехникаСервер.АвтозаполнениеПоМощности):
1. Рантайм-запрос: все элементы `АпкМоделиСХТехники` с заполненной
   `МощностьДвигателя` > 0.
2. Базовая модель → строка K = 1,00, БазоваяМодель = Истина.
3. Прочие модели: **K = МощностьДвигателя(базовой) / МощностьДвигателя(модели)**
   (TD-004/TD-005: K — отношение смен, смены обратно пропорциональны мощности;
   мощный аналог получает K < 1 — согласуется с референсом s02: 0,80 у аналога
   при 1,00 у базовой).
4. Модели без мощности: строка НЕ создаётся (FR-004, вариант «не создавать»);
   их список выводится в сообщение пользователю.
5. Существующие записи с тем же ключом не перезаписываются (только отсутствующие),
   чтобы не затереть ручные правки; о числе созданных — сообщение.
Производительность: один запрос + запись наборов, ≤ 5 с на 100 моделей (NFR-002).

### 4.7 Общий модуль Тх_ТехникаСервер и алгоритм расчёта дефицита

Серверный общий модуль, экспортные функции:
`ВыполнитьЗапросАПК`, `ЧислоДнейПериода`, `КоэффициентНаДату`,
`ЗапросПотребности`, `ЗапросДоступности`, `РассчитатьДефицит`,
`АвтозаполнениеПоМощности`.

Параметры расчёта (форма обработки Тх_РасчетДефицита): Организация,
Подразделение, СценарийПланирования (generic), Период с..по, ВидТехники,
СменВДень (Число, default 1 — Q-001), ВариантОбъема (Минимальный/Вероятный/
Максимальный → суффикс ресурса `_Мин/_Вер/_Макс`, default Вероятный).
Кнопка «Рассчитать и открыть отчёт».

Псевдокод (BSL-стиль):

```
Функция РассчитатьДефицит(Пар)  // Пар: Отборы, СменВДень, Суффикс ("_Вер")
	// ШАГ 1. Потребность (рантайм-запросы к расширению №1)
	//   UNION ALL двух запросов:
	//   а) АпкМеханизированныеРаботыПоГодовомуПлануОбороты
	//      ИЗМЕРЕНИЯ: СценарийПланирования, Организация, Подразделение,
	//        ПериодНачала, ПериодОкончания, ВидРаботы, Техника(=модель)
	//      РЕСУРС:  Смен<Суффикс>  (напр. Смен_Вер)
	//      ТЧ-фильтр: ВидТехники = СХТехника (техника, не оборудование)
	//   б) АпкТранспортныеРаботыПоГодовомуПлануОбороты
	//      Автомобиль(=модель) → колонка МодельТехники, ВидТехники = Автотранспорт
	//   отборы: Сценарий, Организация(если задана), Подразделение(если задано),
	//   ПериодОкончания >= Пар.ДатаС И ПериодНачала <= Пар.ДатаПо
	//   ГРУППИРОВКА: Сценарий, Организация, Подразделение,
	//                ПериодНачала, ПериодОкончания, ВидРаботы,
	//                МодельТехники(=Техника|Автомобиль), ВидТехники
	//   СУММА: Смен<Суффикс> → ПотребностьСмен
	ТЗПотребность = ЗапросПотребности(Пар);

	// ШАГ 2. Доступность (запрос к собственному документу)
	//   Документ.Тх_ПланТехническихРесурсов, Проведен = ИСТИНА,
	//   Принят = ИСТИНА; Сценарий/Подразделение по шапке (те же отборы)
	//   ГРУППИРОВКА: СценарийПланирования, Подразделение,
	//                МодельТехники, ВидТехники
	//   СУММА: Количество → ЕдиницДоступно
	ТЗДоступность = ЗапросДоступности(Пар);
	ПланыЕсть = ТЗДоступность.Количество() > 0;

	// ШАГ 3. Очистка регистра результата по отборам запуска
	УдалитьСтарыеЗаписи(Пар);

	// ШАГ 4-5. По каждой строке потребности
	Для Каждого Стр Из ТЗПотребность Цикл
		Подразделение = Стр.Подразделение;
		Дней = ЧислоДнейПериода(Стр.ПериодНачала, Стр.ПериодОкончания); // календарные, вкл. границы
		БазМодель = Стр.МодельТехники;
		Если Стр.ВидТехники = Автотранспорт Тогда
			// модель в модель, без коэффициентов (Q-005, D-007)
			Дост = Единиц(Подразделение, БазМодель) * Дней * Пар.СменВДень;
			КоэфНеЗадан = Ложь;
		Иначе
			Дост = 0;  КоэфНеЗадан = Ложь;
			Для Каждого М Из ДоступныеМодели(Подразделение) Цикл
				ДоступноСменМ = М.ЕдиницДоступно * Дней * Пар.СменВДень;
				Если М.Модель = БазМодель Тогда
					Дост = Дост + ДоступноСменМ;              // сама базовая модель
				Иначе
					К = КоэффициентНаДату(Стр.ВидРаботы, М.Модель, Стр.ПериодНачала);
					Если К = Неопределено Тогда
						КоэфНеЗадан = Истина;                  // модель ИСКЛЮЧЕНА, пометка (FR-011)
					Иначе
						Дост = Дост + ДоступноСменМ / К;       // TD-004: эквивалент в сменах базовой
					КонецЕсли;
				КонецЕсли;
			КонецЦикла;
		КонецЕсли;
		Дефицит = Макс(0, Окр(Стр.ПотребностьСмен - Дост, 2));   // FR-012
		ЗаписатьСтроку(Тх_ДефицитТехники, Стр, Дост, Дефицит, Дней,
		               КоэфНеЗадан, НЕ ПланыЕсть(Подразделение));
	КонецЦикла;
	Возврат ЧислоЗаписей;
КонецФункции
```

Формулы (фиксация TD-004):
- Семантика: **K = смены_аналога / смены_базовой** (контракт FR-010);
  K = 0,80 → аналог выполнит объём базовой за 0,8 смены (s02).
- Потребность в сменах аналога = ПотребностьСмен(базовой) × K.
- Доступные смены аналога в эквиваленте базовой = смены_аналога / K
  (обратное преобразование при сопоставлении с потребностью базовой модели).
- Автозаполнение: K = Мощн(базовой) / Мощн(аналога).
- `ЧислоДнейПериода` = календарные дни (Окончание − Начало + 1), v1 без
  производственного календаря (FAQ Q1); рабочие дни по графику — v2.
- Группировка периодов: расчёт по интервалам строк техкарт как есть
  (ПериодНачала/ПериодОкончания, Q-002); в отчёте это «Дата начала /
  Дата окончания» — как в референсе s05 (15.09, 25.09). Календарная сетка
  (декада/неделя) с распределением смен (Q-006) — v2.

### 4.8 Обработка Тх_РасчетДефицита

Форма с отборами и параметрами (§4.7), серверный вызов
`Тх_ТехникаСервер.РассчитатьДефицит`, затем `ОткрытьФорму("Отчет.Тх_ДефицитТехники.Форма")`.
Индикация длительной операции — без фоновых заданий (NFR-001): расчёт на объёме
NFR-002 укладывается в интерактивный вызов (цель ≤ 30 с вместе с отчётом).

### 4.9 Роли и доступ

- **Тх_Чтение**: чтение Тх_КоэффициентыПересчетаРабот, Тх_ПланТехническихРесурсов,
  Тх_ДефицитТехники; использование отчёта и обработок (просмотр).
- **Тх_Редактирование**: всё из Тх_Чтение + добавление/изменение/проведение
  документа, добавление/изменение коэффициентов, запуск расчёта и автозаполнения.
- Роли дают права **только на новые объекты** (NFR-004). Для чтения типовых
  данных (регистры годового плана, ТС, справочники АПК) пользователю нужны
  типовые роли ERP/АПК (например, АпкЧтениеРегистровПланированиеРастениеводства) —
  это фиксируется в инструкции по внедрению, не расширением прав.
- Пользователь без обеих ролей не видит подсистему и отчёт (US-004).

## 6. Security / Permissions / Privacy

- **Authorization:** роли §4.9; новая роль не расширяет типовые права (NFR-004).
- **Input validation:** валидация generic-ссылок рантайм-`Тип()` (§4.1);
  неотрицательность и ненулевое деление (K = 0 отклоняется при записи).
- **Sensitive data:** персональных данных нет; данные планов — производственные.
- **Abuse:** расчёт только перезаписывает свой регистр по отборам запуска —
  «чужие» строки других организаций не трогаются (очистка строго по отборам).

## 7. UX / Accessibility (1С-специфика)

- Форма коэффициентов: шапка «Период» + таблица, как s02; пустое состояние —
  подсказка «используйте Заполнение коэффициентов».
- Форма плана техресурсов: 3 закладки с числом принятых единиц в заголовках;
  хоз.номер виден в строке (s04); чекбокс «Принят» default Истина.
- Отчёт: группировки и «Не хватает смен» по s05; пометки незаданных
  коэффициентов/отсутствия планов — условным оформлением, не модальными окнами.
- Все формы — без модальности (NFR-001), ClientServer-вызовы серверных функций.

## 8. Edge Cases

| Case | Expected Behavior |
|------|-------------------|
| Нет коэффициента для доступной модели | модель исключена из пересчёта, строка помечена «коэффициент не задан» (FR-011) |
| Нет проведённых планов техресурсов в подразделении | доступность = 0, строка помечена «план техресурсов отсутствует», дефицит = потребность (NFR-005) |
| Модель без мощности при автозаполнении | строка не создаётся, список моделей — в сообщении (FR-004) |
| K = 0 или отрицательный | отказ записи набора |
| Две базовые модели в одном наборе | отказ записи (FR-003) |
| Расширение №1 отключено | понятное сообщение, расчёт прерван, прошлые результаты в регистре сохранены |
| Период строки техкарты вне диапазона запуска | строка не попадает в расчёт (отбор по пересечению интервалов) |
| ТС принято в планах двух подразделений одного сценария | неблокирующее предупреждение при проведении (§4.4) |
| Пустой результат расчёта | отчёт пуст + сообщение «выполните Расчет дефицита» |
| Повторный запуск с теми же исходными данными | идентичный результат (NFR-005; очистка+перезапись по отборам) |

- **Debugging:** замер производительности расчёта (ЗамерВремени в конфигураторе),
  тексты рантайм-запросов — логируются при параметре отладки обработки.
- **Alerts:** не применимо (офлайн-продукт).

## 13. Migration / Rollout

- **Migration:** нет (новые объекты, данных не существует).
- **Rollout:** установка CFE «ПланированиеТехникиАПК» в рабочую базу,
  db-cfe-admin проверка применимости, назначение ролей.
- **Rollback:** отключение/удаление расширения — типовая конфигурация не
  затронута (NFR-003); данные документов/регистров расширения удаляются
  вместе с ним (задокументировать).
- **Feature flag:** не требуется (подсистема видима только с ролями Тх_*).

## 14. Technical Decisions

### TD-001: Generic-типы вместо прямых ссылок на расширение №1

- **Decision:** все ссылки на объекты расширения №1 — составные generic-типы
  + строковые имена + рантайм-доступ (§4.1); прямые типы только на core ERP.
- **Why:** по документации платформы 8.3/8.5 расширение ссылается типами только
  на основную конфигурацию; предметные объекты АПК живут в другом расширении.
- **Trade-off:** слабее контроль типов на этапе конфигурации → компенсировано
  рантайм-валидацией `Тип("...")` и формами выбора по именам; чуть больше кода.
- **Alternatives:** прямые типы (риск отказа загрузки расширения — не проверено
  эмпирически, кластер упал); перенос объектов АПК к себе (запрещено D-001).

### TD-002: Потребность из регистров годового плана, а не из ТЧ техкарт

- **Decision:** рантайм-запросы к `Апк*РаботыПоГодовомуПлануОбороты`.
- **Why:** быстрее, агрегировано, учитывает «КорректировкаРегистров», не зависит
  от структуры ТЧ (ФАКТ-2).
- **Trade-off:** зависимость от наличия/структуры типового регистра расширения №1
  (при отключении №1 расчёт невозможен — обрабатывается явно).
- **Alternatives:** чтение ТЧ документов (медленнее, корректировки не учтёт).

### TD-003: Двухфазная схема отчёта (расчёт → регистр → СКД)

- **Decision:** СКД читает только собственный регистр Тх_ДефицитТехники;
  заполнение — отдельной обработкой.
- **Why:** СКД-набор с рантайм-запросами к чужому расширению хрупок и медлен;
  двухфазная схема даёт простой отчёт, детерминизм и повторное использование
  результата.
- **Trade-off:** результат устаревает между расчётами (пересчитывается кнопкой);
  лишний регистр.
- **Alternatives:** единый отчёт с произвольным запросом и внешним кодом
  (сложнее, риски СКД+рантайм), расчёт на лету (30 с NFR-002 рискован).

### TD-004: Семантика коэффициента и формулы пересчёта

- **Decision:** K = смены_аналога / смены_базовой (контракт FR-010);
  эквивалент доступности аналога в сменах базовой = смены_аналога / K;
  потребность в сменах аналога = потребность_базовой × K.
- **Why:** однозначно согласуется с референсом s02 (базовая 1,00, аналог 0,80 =
  аналог быстрее) и с автозаполнением по мощности (мощнее → меньше смен).
- **Trade-off:** пользователям, привыкшим к «доле производительности» (1/K),
  нужна подпись в форме — добавлена (§7).
- **Alternatives:** K = производительность (FR-010 формула меняется на деление
  потребности) — математически эквивалентно, но противоречит зафиксированной
  в требованиях семантике; отклонено (см. Requirements feedback п.1).

### TD-005: Автозаполнение K = Мощн(базовой) / Мощн(аналога)

- **Decision:** обратно пропорционально мощности (производительность ∝ мощность).
- **Why:** прямое следствие TD-004; стартовые оценки без ручного ввода (FR-004).
- **Trade-off:** мощность — грубый прокси производительности (ширина захвата
  и пр. не учитываются); значения правятся вручную.
- **Alternatives:** через УЭГа/сменные нормы типовых норм (сложно, зависит от
  заполняемости норм).

### TD-006: Префикс «Тх_» и имя расширения «ПланированиеТехникиАПК»

- **Decision:** префикс «Тх_» для всех объектов/ролей; имя CFE — 
  «ПланированиеТехникиАПК».
- **Why:** изоляция имён от будущих версий типовой/других расширений (NFR-003);
  короткий префикс читаем.
- **Trade-off:** длиннее непрефиксных имён (Q-007 Option B отклонена —
  standing-инструкция ночного прогона предпочла изоляцию).
- **Alternatives:** без префикса (риск коллизии при обновлениях).

### TD-007: Периоды расчёта — интервалы строк техкарт

- **Decision:** расчёт по исходным интервалам (ПериодНачала/ПериодОкончания),
  в отчёте — «Дата начала / Дата окончания» как в s05; дни периода — календарные.
- **Why:** точность до исходных данных, простота, соответствует референсу s05.
- **Trade-off:** «рваные» периоды в отчёте при большом числе строк.
- **Alternatives:** календарная сетка (декада/неделя) с распределением смен
  пропорционально дням (Q-002-B/Q-006) — отложено в v2.

## 16. Implementation FAQ

**Q1: Рабочие или календарные дни в доступных сменах?**
A: v1 — календарные дни интервала (границы включены) × СменВДень (параметр
расчёта, default 1). Производственный календарь/графики — v2 (не блокер).

**Q2: Почему СменВДень — параметр, а не константа?**
A: Q-001 Option A: 1 смена/день на ТС по умолчанию, гибкость через параметр
обработки расчёта. Значение сохраняется в регистре результата (ресурс СменВДень)
для прозрачности.

**Q3: Какой ресурс регистра годового плана брать?**
A: Ресурсы тройные (`_Мин/_Вер/_Макс`). Параметр «ВариантОбъема», default
«Вероятный» → `Смен_Вер`.

**Q4: Учитывается ли оборудование в дефиците?**
A: Нет (D-007, Q-005-B): ТЧ «Оборудование» в плане техресурсов ведётся, но в
расчёт не входит. Механизированные работы (вид СХТехника) — с коэффициентами;
транспортные работы (вид Автотранспорт) — модель в модель без коэффициентов.

**Q5: Что если одно ТС в двух планах одного сценария в разных подразделениях?**
A: Неблокирующее предупреждение при проведении; расчёт возьмёт его в доступность
обоих подразделений (двойной счёт возможен) — осознанное допущение, задокументировано.

**Q6: Почему Подразделение — СтруктураПредприятия, а не «Подразделения»?**
A: Измерение типового регистра годового плана и шапки техкарт —
`CatalogRef.СтруктураПредприятия` (core ERP); наш документ обязан совпадать
типом для соединения. Справочника «Подразделения» в ERP 2.5 нет (Requirements
feedback п.2).

**Q7: Почему СценарийПланирования — generic?**
A: `АпкСценарииПланирования` находится в расширении №1, не в core ERP —
на прямые типы ссылаться нельзя (Requirements feedback п.3).

**Q8: Формы другого расширения открывать можно?**
A: Да — динамически по имени (`ОткрытьФорму("Справочник.ВидыРаботСотрудников.ФормаВыбора")`),
без заимствования в расширение №2.

**Q9: Нужны ли движения документа плана техресурсов?**
A: Нет: расчёт читает ТЧ запросом по `Проведен = ИСТИНА`. Движения — лишний объект.

**Q10: Когда Vanessa/e2e запускать?**
A: Vanessa TestClient требует GUI — ночью только авторинг .feature; запуск — днём
в интерактивной сессии (1c-headless-capability). E2E — после публикации базы.

## 18. Requirements Feedback (изменения/уточнения — на утреннее ревью)

Дизайн не меняет контракт требований; зафиксированы уточнения и отклонения
от рекомендаций (все — внутри полномочий design-решений, ревью утром):

1. **Формула коэффициента.** Промпт-факт «K = производительность аналога,
   потребность = базовая / K» эквивалентен контракту FR-010 «K = смены_аналога /
   смены_базовой» (производительность = 1/K). Дизайн следует FR-010 как контракту:
   эквивалент доступности = смены_аналога / K, автозаполнение K = Мб/Ма.
   Результат численно одинаков; семантика K — «меньше K → мощнее аналог» (s02).
2. **Подразделение = CatalogRef.СтруктураПредприятия** (не «Подразделения»):
   так в измерениях типового регистра годового плана и шапках техкарт; прямое
   следствие требования сопоставимости разрезов (FR-008/FR-009).
3. **СценарийПланирования — объект расширения №1** (АпкСценарииПланирования),
   не core ERP: используется generic-тип (уточнение допущения из ТЗ на дизайн).
4. **Префикс «Тх_»** — решение по Q-007 в пользу Option A (изоляция имён),
   а не рекомендованной Option B; standing-инструкция предпочла надёжность.
5. **Q-001..Q-007 закрыты в дизайне:** Q-001 → параметр СменВДень=1;
   Q-002 → расчёт по интервалам строк (Option A фактически, сетка — v2);
   Q-003 → только конкретные ТС; Q-004 → Option B; Q-005 → Option B;
   Q-006 → отложено (актуально только с календарной сеткой v2);
   Q-007 → префикс Тх_.
6. **FR-004, вариант отсутствия мощности:** строка НЕ создаётся, список моделей —
   в сообщении (выбран вариант «не создавать» из двух, допущенных требованием).
