# Feature: Редизайн «Планирования техники АПК» — расчёт потребности в технике по техкартам

> Status: Draft
> Source: .ai/sdd/ideas/002-redesign-planirovaniia-tekhniki.md
> Spec: 002-redesign-planirovaniia-tekhniki
> Supersedes: .ai/sdd/specs/001-analiz-defitsita-tekhniki/ (устарела в части форм/типов; использовать только как справочник фактов)

## Overview

Перепроектирование расширения «ПланированиеТехникиАПК» (CFE для 1С:ERP АПК):
(1) все реквизиты объектов и форм получают конкретные типы; (2) контроль совместимости
сцепки «техника ↔ прицепное/сцепное оборудование»; (3) новая обработка «Формирование
плана работ техники» — автозаполнение документа потребности по данным ПРОВЕДЁННЫХ
технологических карт на поле, в разрезе моделей, с коэффициентами замещения и сравнением
с техникой, доступной подразделению; результат корректируется пользователем; (4) удаление
регистра Тх_КоэффициентыПересчетаРабот; (5) устранение дублей синонимов; (6) правовые
тесты на обычном пользователе ИБ «Агроном».

## Business Context

Техкарты на поле планируют работы до МОДЕЛЕЙ техники (не до конкретных ТС). Хозяйству
нужно знать: сколько и каких моделей техники требуется в период по подразделению
выращивания, и хватает ли доступной подразделению техники (распределение —
Документ.АпкПланТехническихРесурсов). Взаимозаменяемость моделей оценивается
паспортными характеристиками (мощность двигателя, ширина обработки, грузоподъёмность,
вместимость, объём бункера, КоэффициентПереводаВУЭГА). Сейчас план заполняется вручную,
формы содержат generic-типы — медленно и неудобно.

## User Stories

### US-001: Автоформирование плана потребности

**As a** агроном-планировщик
**I want to** запустить обработку «Формирование плана работ техники» с параметрами
(организация, подразделение, сценарий планирования, период) и получить автозаполненный
документ потребности
**So that** не собирать потребность вручную — она следует из проведённых техкарт.

**Acceptance Criteria:**
- [ ] Обработка читает ПРОВЕДЁННЫЕ техкарты на поле за период; техкарты чужих
      подразделений (подразделение выращивания ≠ заданному) не учитываются.
- [ ] Потребность считается в разрезе МОДЕЛЕЙ техники и прицепных/сцепных устройств.
- [ ] Доступность техники подразделения берётся из Документ.АпкПланТехническихРесурсов.
- [ ] Результат записывается в документ, который пользователь может корректировать.

### US-002: Совместимость сцепки при выборе

**As a** агроном-планировщик
**I want to** при выборе модели техники видеть в колонке «Оборудование»/«Прицеп» только
совместимые позиции
**So that** не составить невозможную сцепку (СХ-трактор с прицепом автотранспорта).

**Acceptance Criteria:**
- [ ] Модель из АпкМоделиСХТехники → оборудование только из АпкМоделиСХОборудования.
- [ ] Модель из АпкМоделиАвтотранспорта → прицеп только из АпкМоделиПрицепов.

### US-003: Понятные имена объектов (без дублей)

**As a** пользователь
**I want to** различать объекты в интерфейсе: наш документ ≠ АпкПланТехническихРесурсов,
наш отчёт ≠ наш регистр
**So that** не путаться в командах и списках.

**Acceptance Criteria:**
- [ ] Синоним документа Тх_ПланТехническихРесурсов — «Потребность в технике»
      (внутреннее имя не меняется).
- [ ] Отчёт Тх_ДефицитТехники и регистр Тх_ДефицитТехники имеют разные синонимы.

### US-004: Права на обычном пользователе

**As a** администратор
**I want to** проверить видимость раздела/команд Тх_ у пользователя ИБ «Агроном» с
назначенными Тх_-ролями
**So that** права реально работают (не на ПолныхПравах).

**Acceptance Criteria:**
- [ ] «Агроном» открывает базу и видит раздел/команды Тх_ согласно ролям.
- [ ] Правовые тесты выполняются только под «Агрономом»; VA-прогоны функциональности — под админом.

## Functional Requirements

### FR-001: Конкретные типы реквизитов объектов и форм — Must Have

WHEN пользователь открывает любую форму или список объектов расширения
THE SYSTEM SHALL показывать поля с конкретными типами (без диалога «Выбор типа данных»
в местах, где тип известен бизнесом)
SO THAT формы проходимы для НТТ/Vanessa и удобны пользователю.

Типы (по решению пользователя):
- «Сценарий планирования» → `СправочникСсылка.АпкСценарииПланирования`;
- «Модель техники» → составной `АпкМоделиСХТехники` | `АпкМоделиАвтотранспорта`
  (единственный допустимый составной тип — бизнес-необходим);
- «Вид работы» → `СправочникСсылка.ВидыРаботСотрудников`;
- прицепное/сцепное: `АпкМоделиСХОборудования` / `АпкМоделиПрицепов` (см. FR-002);
- прочие реквизиты (Организация, Подразделение, ТС, работа и др.) — конкретные типы
  соответствующих справочников/документов конфигурации.

### FR-002: Контроль совместимости сцепки — Must Have

WHEN пользователь выбирает модель техники в строке плана
IF модель относится к АпкМоделиСХТехники
THE SYSTEM SHALL допускать в связанном поле только `Справочник.АпкМоделиСХОборудования`
IF модель относится к АпкМоделиАвтотранспорта
THE SYSTEM SHALL допускать в связанном поле только `Справочник.АпкМоделиПрицепов`
SO THAT невозможные сцепки не составляются (связанный выбор/фильтрация на форме).

### FR-003: Обработка «Формирование плана работ техники» (релиз 1) — Must Have

WHEN пользователь выполняет обработку с параметрами (организация, подразделение,
сценарий планирования, период)
THE SYSTEM SHALL:
1. прочитать данные ПРОВЕДЁННЫХ техкарт на поле за период — только по заданному
   подразделению выращивания (точные регистры — определить в design-фазе через
   rlm-tools-bsl по APKModSrc, не угадывать);
2. рассчитать потребность в МОДЕЛЯХ техники и прицепных/сцепных устройствах
   (техкарты до ТС не планируют);
3. применить коэффициенты замещения моделей (FR-004);
4. сопоставить потребность с техникой, ДОСТУПНОЙ подразделению, по данным
   Документ.АпкПланТехническихРесурсов;
5. заполнить документ потребности, который пользователь корректирует вручную
SO THAT план следует из техкарт, а не вводится руками.

### FR-004: Коэффициенты замещения моделей — Must Have

THE SYSTEM SHALL вычислять коэффициенты замещения моделей по существующим паспортным
реквизитам (правило: если «ручной» реквизит заполнен — он базовый, иначе старт по
мощности двигателя там, где она есть):

| Вид модели | Ручной реквизит (приоритет) | Старт (если пусто) |
|---|---|---|
| АпкМоделиСХТехники | КоэффициентПереводаВУЭГА / ШиринаОбработки / ОбъемБункера | МощностьДвигателя |
| АпкМоделиСХОборудования | ШиринаОбработки | — (нет мощности) |
| АпкМоделиАвтотранспорта | Грузоподъемность / Вместимость | МощностьДвигателя |
| АпкМоделиПрицепов | Грузоподъемность / Вместимость | — (нет мощности) |

Коэффициент = значение реквизита модели / значение реквизита базовой модели
(детализация формул — design-фаза).

### FR-005: Удаление Тх_КоэффициентыПересчетаРабот — Must Have

THE SYSTEM SHALL удалить объекты регистра сведений Тх_КоэффициентыПересчетаРабот
(вместе с формой записи) из расширения
SO THAT устаревший механизм коэффициентов «видов работ» (заменён модельными
коэффициентами FR-004) и его рантайм-баг (вызов несуществующего
`ИмяСправочникаМоделейСХТехники`) полностью уходят.

### FR-006: Устранение дублей синонимов — Must Have

THE SYSTEM SHALL изменить ТОЛЬКО синонимы (внутренние имена не меняются — нет миграций):
- Документ Тх_ПланТехническихРесурсов → «Потребность в технике»;
- синонимы отчёта Тх_ДефицитТехники и регистра Тх_ДефицитТехники — различные
  (конкретные значения — Q-001);
- Документ.АпкПланТехническихРесурсов (АПК) остаётся «План технических ресурсов»
  (чужой объект, не трогаем)
SO THAT одноимённые объекты различимы в интерфейсе.

### FR-007: Правовые тесты на пользователе «Агроном» — Should Have

WHEN роли Тх_ назначены пользователю ИБ «Агроном»
THE SYSTEM SHALL обеспечивать видимость раздела/команд Тх_ согласно ролям, и это
проверяется тестами именно под «Агрономом» (не под администратором с ПолнымиПравами)
SO THAT права реально работают.

## Non-Functional Requirements

### NFR-001: НТТ/Vanessa-проходимость
- После ретайпинга все поля форм проверяемого документа/обработки вводимы через НТТ
  («ввожу текст» в ссылочные поля, перечисления — надёжны), generic-полей нет.

### NFR-002: Производительность
- Расчёт потребности за период по техкартам выполняется серверно; объём демо-базы
  (2014–2015) — без таймаутов VA.

### NFR-003: Совместимость
- Расширение не модифицирует типовые объекты; прямые ссылки на типы конфигурации
  (Апк*, ТранспортныеСредства и др.) в метаданных CFE принимаются платформой
  8.5.4.1683 (проверить на первой загрузке — иначе эскалация, не откат в generic).

### NFR-004: Тестируемость прав
- Правовые сценарии — только под обычным пользователем ИБ; функциональные VA-прогоны —
  под админом.

## Out of Scope (релиз 1)

- Предложения замен техникой ДРУГИХ подразделений с учётом расстояний и затрат на
  перемещение (своим ходом / трал + спецразрешения) — future, зафиксировать в FAQ/roadmap.
- Переименование внутренних имён объектов (нет миграций).
- Модификация чужих объектов: Документ.АпкПланТехническихРесурсов, расширение
  «Расширение_АПК», VAExtension.
- Ручное редактирование коэффициентов замещения (используются существующие реквизиты
  моделей; отдельный регистр коэффициентов удалён).

## Decisions

### D-001: Направление — эволюционный редизайн (A)

**Decision:** каркас объектов сохраняем, ретайпинг на месте, документ переосмысляем
как результат расчёта, добавляем обработку, регистр коэффициентов работ удаляем.
**Reason:** без миграций, переиспользование форм/ролей/сценариев 01–02.
**Source:** ответ пользователя «A» (2026-10-09).

### D-002: Синоним документа — «Потребность в технике»

**Decision:** вариант В-1=1: документ-результат расчёта, корректируемый пользователем.
**Source:** ответ пользователя «В-1=1».
**Impacts:** FR-006, US-001.

### D-003: Таблица коэффициентов замещения утверждена

**Decision:** схема «ручной реквизит (приоритет) → старт по мощности двигателя»
по видам моделей (таблица FR-004).
**Source:** ответ пользователя «В-2=ok».
**Impacts:** FR-004.

### D-004: Тестовые расчёты на периодах 2014–2015

**Decision:** тесты/VA-сценарии расчёта ведём на существующих демо-данных техкарт
2014–2015 (демо-двиг не плодим).
**Source:** ответ пользователя «В-3=ok».
**Impacts:** FR-003, NFR-002, тесты.

### D-005: Тх_КоэффициентыПересчетаРабот — удалить

**Decision:** вариант В-4=2: объект регистра удаляем из расширения; рантайм-баг
закрывается удалением (чинить форму записи не нужно).
**Source:** ответ пользователя «В-4=2».
**Impacts:** FR-005; регистр Тх_ДефицитТехники остаётся источником отчёта.

### D-006: Переименования — только синонимы; разрез — модели

**Decision:** из redesign-prompt §10 (решено пользователем ранее): внутренние имена
не меняем; разрез плана — модели техники и прицепных устройств; доступность — из
Документ.АпкПланТехническихРесурсов; правовые тесты — «Агроном».
**Source:** redesign-prompt §10.1–10.5.

## Questions

### Q-001: Синонимы для пары «отчёт/регистр Тх_ДефицитТехники»

**Status:** open
**Why it matters:** FR-006 требует различные синонимы; конкретные значения влияют
на UI и сценарии VA (шаги навигации по заголовкам).
**Recommended:** Option A — отчёт: «Дефицит техники» (пользовательский термин из
презентации), регистр: «Дефицит техники (данные)» (служебный источник отчёта).

| Option | Answer | Choose this if... | Impact |

| A | отчёт «Дефицит техники», регистр «Дефицит техники (данные)» | согласны с рекомендацией | FR-006 |
| B | отчёт «Анализ дефицита техники», регистр «Дефицит техники» | хотите подчеркнуть аналитическую роль отчёта | FR-006, VA-шаги |
| Custom | пользовательский вариант | — | FR-006 |

### Q-002: Структура строк документа потребности

**Status:** open
**Why it matters:** определяет ТЧ документа, форму и результат обработки (FR-003).
**Recommended:** Option A — сохранить трёхчастную структуру ТЧ (ОсновнаяТехника:
модель+оборудование / Оборудование / Автотранспорт: модель+прицеп) с добавлением
количественных показателей из техкарт (смен/часов) в строки; ретайпировать колонки.

| Option | Answer | Choose this if... | Impact |
|--------|--------|-------------------|--------|
| A | три ТЧ как сейчас + количественные колонки | минимальные изменения форм/тестов | FR-003, forms |
| B | единая ТЧ «Потребность» с составным видом строки | хотите единообразие | больше правок формы, миграция структуры документа |
| Custom | пользовательский вариант | — | — |

## Glossary

- **Техкарта** — Документ.АпкТехнологическиеКартыНаПоле (проведённый): работы, СХ-техника
  (модель+оборудование), автотранспорт (модель+прицеп), доп.оборудование.
- **Подразделение выращивания** — подразделение, к которому относится поле техкарты.
- **Доступность** — техника, распределённая подразделению Документ.АпкПланТехническихРесурсов.
- **Коэффициент замещения** — отношение паспортного реквизита модели к реквизиту базовой модели.
- **Сцепка** — пара «модель техники + прицепное/сцепное оборудование» с правилом
  совместимости (СХ ↔ СХ-оборудование; автотранспорт ↔ прицепы).
