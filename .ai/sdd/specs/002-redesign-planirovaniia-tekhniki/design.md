# Design: Редизайн «Планирования техники АПК» — расчёт потребности по техкартам

> Requirements: @requirements.md (approved, D-001..D-008)
> Status: Draft
> Спека: 002-redesign-planirovaniia-tekhniki
> Факты собраны через rlm-tools-bsl по индексам APKModSrc (АПК 2.5.27.88) и APKTechPlan (2026-10-09); канонические ответы — §6.1.

## 1. Summary

Эволюционный редизайн расширения (D-001): (а) ретайпинг всех реквизитов объектов и форм
с generic-TypeId на конкретные `cfg:`-типы; (б) контроль совместимости сцепки на форме
документа; (в) новая обработка «Формирование плана работ техники», читающая обороты
двух регистров накопления годового плана АПК (техника/автотранспорт) за период по
подразделению выращивания, сопоставляющая потребность в МОДЕЛЯХ с доступностью из
проведённых АпкПланТехническихРесурсов (через ТС→АпкМодель), с модельными коэффициентами
замещения; результат — строки документа «Потребность в технике», корректируемого
пользователем; (г) удаление регистра Тх_КоэффициентыПересчетаРабот с обслуживающей
обработкой и переход расчёта дефицита на модельные коэффициенты; (д) раздельные
синонимы; (е) правовые тесты под «Агроном».

## 3. Technical Approach (выбранный путь)

1. **Ретайпинг** — точечная замена в XML объектов `<Type><v8:TypeId>GUID</v8:TypeId></Type>`
   → `<Type><v8:Type>cfg:CatalogRef.X</v8:Type>[<v8:Type>…</v8:Type>…]</Type>`
   (формат, идентичный типовому APKModSrc; Designer принимает оба, наш — уже грузится).
   Аналогично в Form.xml (там уже `v8:Type`-строки — меняем состав типов).
   Правки делаем python-скриптами (utf-8-sig, CRLF), не руками.
2. **Обработка** — новый объект `DataProcessor.Тх_ФормированиеПланаРаботТехники`
   (синоним «Формирование плана работ техники»), серверная логика — новые экспортные
   функции в существующем `Тх_ТехникаСервер` (без нового общего модуля; Privileged=false,
   ExternalConnection=true — как сейчас).
3. **Удаление** — `Тх_КоэффициентыПересчетаРабот` (объект+обе формы) и
   `Тх_ЗаполнениеКоэффициентов` (обработка+форма — сервисная, существовала только
   для наполнения регистра). Права из ролей, строка подсистемы, тесты — убрать.
4. **Пайплайн каждой правки** (§9 промта): pre_load_validate → bsl-ls → **v8std** →
   db-load-xml Full -UpdateDB → свежий load_log → при структурных изменениях
   kill 1cv8* → designer_agent apply → round-trip (dump_extension + compare) → VA.

## 5. Data Model / State

### 5.1 Документ Тх_ПланТехническихРесурсов — целевые типы

Шапка (Attribute, сейчас generic-TypeId → конкретный тип):

| Реквизит | Тип |
|---|---|
| Организация | `CatalogRef.Организации` |
| Подразделение | `CatalogRef.СтруктураПредприятия` |
| СценарийПланирования | `CatalogRef.АпкСценарииПланирования` |
| Комментарий | `xs:string` (неограниченная строка) |

ТЧ (все три — колонки ретайпируются, новые добавляются; D-008):

ТЧ **ОсновнаяТехника** (строка = модель СХ-техники в сцепке с СХ-оборудованием на работе):

| Колонка | Тип | Источник/назначение |
|---|---|---|
| МодельТехники | `CatalogRef.АпкМоделиСХТехники` (однотипный!) | из техкарты (МеханизированныеРаботы.Техника) |
| Оборудование | `CatalogRef.АпкМоделиСХОборудования` | из техкарты (…Оборудование) |
| ВидРаботы | `CatalogRef.ВидыРаботСотрудников` | из техкарты |
| ПотребностьСмен | `xs:decimal(10,3)` | Σ Смен_Вер по техкартам за период |
| ПотребностьЧасов | `xs:decimal(10,3)` | Σ Часов_Вер |
| ДоступноЕдиниц | `xs:decimal(5,0)` | ТС этой модели, доступные подразделению |
| Количество | `xs:decimal(5,0)` | расчётные единицы = ОКРВВЕРХ(ПотребностьСмен / (ДнейПериода × СменВдень)); правится пользователем |
| Принят | `xs:boolean` | дефолт Истина (BeforeAddRow-паттерн, ШАГ 0 baseline) |
| ТранспортноеСредство | `CatalogRef.ТранспортныеСредства` | опционально: конкретное ТС при ручной корректировке |
| Комментарий | `xs:string` | |

ТЧ **Автотранспорт** (строка = модель автотранспорта с прицепом):

| Колонка | Тип | Источник |
|---|---|---|
| МодельТехники | `CatalogRef.АпкМоделиАвтотранспорта` | ТранспортныеРаботы.Автомобиль |
| Оборудование | `CatalogRef.АпкМоделиПрицепов` | ТранспортныеРаботы.Прицеп |
| ВидРаботы | `CatalogRef.ВидыРаботСотрудников` | из техкарты |
| ПотребностьСмен / ПотребностьЧасов | `xs:decimal` | Σ Смен_Вер / Часов_Вер |
| ДоступноЕдиниц / Количество / Принят / ТранспортноеСредство / Комментарий | как выше | |

ТЧ **Оборудование** — ретайпируется (МодельТехники → `CatalogRef.АпкМоделиСХОборудования`,
Принят/Количество/Комментарий), НЕ автозаполняется (см. FAQ Q1). Колонки
ВидРаботы/Потребность* к ней не добавляются.

Примечание: составной тип «Модель техники» (АпкМоделиСХТехники | АпкМоделиАвтотранспорта)
из FR-001 реализован НЕ одним реквизитом, а разными ТЧ (однотипный реквизит в каждой ТЧ) —
это сильнее FR-002 (тип прицепного в ТЧ жёстко задан видом ТЧ) и упрощает НТТ (NFR-001).
Шапка и ТЧ документа полностью типизированы; составные типы остаются только там, где
бизнес-необходимы (нулевое количество).

### 5.2 Регистр Тх_ДефицитТехники — целевые типы

Измерения: Организация → `CatalogRef.Организации`; Подразделение →
`CatalogRef.СтруктураПредприятия`; СценарийПланирования → `CatalogRef.АпкСценарииПланирования`;
ПериодНачала/ПериодОкончания → `xs:dateTime`; ВидРаботы → `CatalogRef.ВидыРаботСотрудников`;
МодельТехники → составной `АпкМоделиСХТехники|АпкМоделиАвтотранспорта|АпкМоделиСХОборудования|АпкМоделиПрицепов`
(единственный допустимый составной — регистр агрегирует все 4 вида моделей);
ВидТехники → `EnumRef.Тх_ВидыТехники` (свой enum, сохраняется).
Ресурсы — числа/булевы, уже конкретные (ПотребностьСмен, ДоступноСмен, НехватаетСмен,
ДнейПериода, СменВДень, КоэффициентНеЗадан, ПланТехресурсовОтсутствует).

### 5.3 Контроль сцепки (FR-002)

Правило: АпкМоделиСХТехники ↔ ТОЛЬКО АпкМоделиСХОборудования;
АпкМоделиАвтотранспорта ↔ ТОЛЬКО АпкМоделиПрицепов.
Реализация — структурно (типы колонок ТЧ уже несовместимы с неверной сцепкой, §5.1) +
форма (§10): при выборе в колонке «Оборудование» списка выбора фильтруется по таблице,
принадлежащей выбранной «МодельТехники»; серверная валидация при записи
(Тх_ТехникаСервер.ВалидироватьСцепку — контроль ТипЗнч пары, отказ записи).

### 5.4 Обработка Тх_ФормированиеПланаРаботТехники (новая)

Форма: параметры — Организация (`CatalogRef.Организации`), Подразделение
(`CatalogRef.СтруктураПредприятия`), Сценарий (`CatalogRef.АпкСценарииПланирования`),
Период с…по (`xs:dateTime`), ДнейПериода (число, по умолчанию = дней между датами),
СменВдень (число, 1..3, по умолчанию 1). Кнопка «Сформировать» (явная `<Button>` +
`Form.Command.Сформировать`, §8 промта). Результат: создаёт НОВЫЙ документ
«Потребность в технике» (Дата=ТекущаяДатаСеанса, шапка из параметров) и заполняет ТЧ.
Опция «Перезаполнить текущий документ» — если обработка открыта из существующего.

### 5.5 Удаление Тх_КоэффициентыПересчетаРабот (FR-005, TD-004)

Удаляются: InformationRegisters/Тх_КоэффициентыПересчетаРабот.xml (+каталог Forms:
Тх_ФормаЗаписи, Тх_ФормаСписка), DataProcessors/Тх_ЗаполнениеКоэффициентов.xml (+форма),
строки в Configuration.xml (ChildObjects), Subsystems/Тх_ПланированиеТехники/…Content,
права в Roles/Тх_Чтение/Rights.xml и Тх_Редактирование/Rights.xml.
В Тх_ТехникаСервер удаляются: КоэффициентНаДату (356), ТочностьКоэффициента (338),
блок записи наборов записей (955), валидация регистра (1178) и смежные.
Данные регистра (периодические коэффициенты «работа×модель») теряются — принято (D-005);
замена — модельные коэффициенты §6.4 (не требуют хранения: считаются из реквизитов
моделей на лету).

## 6. Источники данных (канонические ответы rlm-tools-bsl)

### 6.1 Потребность — данные ПРОВЕДЁННЫХ техкарт (FR-003.1-2)

Проведение Документ.АпкТехнологическиеКартыНаПоле делегировано в
ПроведениеДокументов.ОбработкаПроведенияДокумента; модуль менеджера пишет наборы
записей в регистры накопления (manager_tables, v15 index). Техника — в ДВУХ
регистрах накопления вида **Turnovers**:

- **РегистрНакопления.АпкМеханизированныеРаботыПоГодовомуПлану**:
  измерения: СценарийПланирования, Организация, **Подразделение** (подразделение
  выращивания), Поле, Культура, ГодУрожая, Технология, Услуги, Опционально,
  Вероятность, **ПериодНачала, ПериодОкончания**, ВидРаботы, ХарактеристикаРаботы,
  **Техника** (`АпкМоделиСХТехники`), **Оборудование** (`АпкМоделиСХОборудования`),
  ЕдВСцепке, МаркаТоплива, ЕдиницаДопОбъема, Расценка, БазаНачисления,
  СменнаяНормаВыработки, СменнаяНормаВыработки_Ед, ВедущаяЕдиницаОбъемов,
  КлючСвязи, КлючСвязиОсновнойРаботы;
  ресурсы: **Смен_Мин/Смен_Вер/Смен_Макс, Часов_Мин/_Вер/_Макс**, Гектаров_*, Тонн_*,
  УЭГ_*, ДопОбъемРабот_*, РасходГСМ_*, ЗП_*.
- **РегистрНакопления.АпкТранспортныеРаботыПоГодовомуПлану**: те же служебные
  измерения + **Автомобиль** (`АпкМоделиАвтотранспорта`), **Прицеп**
  (`АпкМоделиПрицепов`), ПунктОтправки/ПунктНазначения, Плечо;
  ресурсы: **Рейсов_*, Тонн_*, Километров_*, ТКм_*, Смен_*, Часов_*** (Min/Вер/Max).

Запрос потребности (8.5, dot-синтаксис виртуальной таблицы оборотов + суффикс, §8 промта):

```
ВЫБРАТЬ Техника, Оборудование, ВидРаботы,
    СУММА(СменВер) КАК ПотребностьСмен, СУММА(ЧасовВер) КАК ПотребностьЧасов
ИЗ РегистрНакопления.АпкМеханизированныеРаботыПоГодовомуПлану.Обороты(
    &ПериодС, &ПериодПо, , Подразделение = &Подразделение
        И СценарийПланирования = &Сценарий И Организация = &Организация).Oborot
```
(аналогично для транспортного регистра: Автомобиль, Прицеп, Смен_Вер/Часов_Вер;
точный синтаксис 8.5 уточняется на первой компиляции — паттерн из
Тх_ТехникаСервер.ЗапросПотребности релиза 001).

Отбор по подразделению выращивания — измерение Подразделение (В ИЕРАРХИИ —
включая дочерние, если задано групповое; параметр «включая подчинённые» = ИСТИНА).
Значения — *_Вер (вероятностный план — базовый вариант годового планирования АПК,
учитывает Вероятность/Опционально; TD-006). Период — пересечение отборов
ПериодНачала/ПериодОкончания с заданным окном (первичная версия: обороты
по периоду регистрации; уточнение — FAQ Q2).

### 6.2 Доступность — Документ.АпкПланТехническихРесурсов (FR-003.4)

Структура: шапка Организация, СценарийПланирования, ПредставлениеПодразделений(строка);
ТЧ Подразделения(Подразделение→СтруктураПредприятия); ТЧ Техника/Оборудование/
Автотранспорт/Прицепы — по колонке ТранспортноеСредство (`CatalogRef.ТранспортныеСредства`).
Механизм типового заполнения (форма, строки 236–265):
`РегистрСведений.АпкИсторияТранспортныхСредств.СрезПоследних(НаДату,
Организация=&Организация И ЭксплуатирующееПодразделение В ИЕРАРХИИ (&Подразделения))`
с ПравоСобственности ∈ (ВСобственности, Арендовано), разложение по ТС.АпкТипТС
(СХТехника/СХОборудование/Автотранспорт/Прицепы).

Наш запрос доступности: проведённые АпкПланТехническихРесурсов по
Организация+СценарийПланирования, где заданное подразделение В ИЕРАРХИИ
ТЧ.Подразделения.Подразделение; из их 4 ТЧ собираем ТС; JOIN
`Справочник.ТранспортныеСредства` по реквизиту **АпкМодель** (составной на все 4
каталога моделей — канонический мост ТС→модель); группировка КОЛИЧЕСТВО(*) по моделям
в разрезе ТипТС. Если документ не найден — ДоступноЕдиниц = 0, в шапке результата
флаг «План распределения техники отсутствует» (ПланТехресурсовОтсутствует-паттерн
релиза 001).

### 6.3 Заполнение документа (FR-003.5)

Для каждой строки потребности: подобрать ДоступноЕдиниц (§6.2); если модель доступна
частично/полностью — Количество = ОКРВВЕРХ(ПотребностьСмен / (ДнейПериода × СменВдень)),
ДоступноЕдиниц из §6.2; если модель недоступна вовсе — применить замещение §6.4;
если замещение не найдено — строка с ДоступноЕдиниц=0 (дефицит, виден в отчёте).
Строки сортируются по ВидРаботы, Период. Пользователь правит всё вручную после.

### 6.4 Коэффициенты замещения моделей (FR-004, D-003, TD-003)

Функция `Тх_ТехникаСервер.КоэффициентЗамещения(МодельОригинал, МодельЗамены)`:

| Вид моделей | Приоритет реквизитов (первый заполненный) | Старт (если все пусты) |
|---|---|---|
| АпкМоделиСХТехники | КоэффициентПереводаВУЭГА → ШиринаОбработки → ОбъемБункера | МощностьДвигателя |
| АпкМоделиСХОборудования | ШиринаОбработки | — (нет) |
| АпкМоделиАвтотранспорта | Грузоподъемность → Вместимость | МощностьДвигателя |
| АпкМоделиПрицепов | Грузоподъемность → Вместимость | — (нет) |

`К = Реквизит(МодельЗамены) / Реквизит(МодельОригинала)`
(`МощностьДвигателяМодели` уже есть в Тх_ТехникаСервер).
Пересчёт: `Смены_Замены = Смены_Оригинала / К` (пример пользователя: ширина замены
в 1,5 раза больше → смен в 1,5 раза меньше).
Подбор замены (релиз 1, эвристика): среди доступных моделей ТОГО ЖЕ вида (сцепка
совместима по построению), для которых К ≥ 1 и та же ЕдВСцепке-совместимость,
берём с максимальным К; если ни у одной К ≥ 1 — берём max(К) < 1 (замена медленнее,
смен растут — честно показать пользователю). Замена фиксируется в строке
(МодельТехники := модель замены, Комментарий := «замещение: <оригинал>, К=…»).
Ручные реквизиты (КоэффициентПереводаВУЭГА и пр.) хранятся в самих моделях АПК —
наш регистр хранения коэффициентов удалён (§5.5); редактирование — в карточке
модели (типовой функционал АПК).

## 9. Edge Cases

| Случай | Поведение |
|---|---|
| Нет проведённых техкарт за период | Пустой результат + сообщение «Техкарты за период не найдены», документ не создаётся |
| Нет проведённого АпкПланТехническихРесурсов | ДоступноЕдиниц=0, флаг в шапке результата, замещение не выполняется (нечем) |
| У модели все «ручные» реквизиты пусты и нет МощностьДвигателя | КоэффициентНеЗадан: замещение не выполняется, строка помечается (ресурс регистра дефицита уже есть) |
| Техкарта с пустой Техникой/Оборудованием | Строка пропускается (оборудование может быть пустым — сцепка без прицепного валидна; техника пустая — строка игнорируется) |
| Опционально/Вероятность в техкарте | Учитываются типовой АПК-логикой записи *_Вер; дополнительно НЕ фильтруем (пользователь решает; FAQ Q3) |
| Подразделение задано группой | В ИЕРАРХИИ — включаются дочерние (и в потребности, и в доступности) |
| Замена найдена, но К < 1 | Берётся max(К), смены пересчитаны вверх, комментарий помечает «замена медленнее» |
| Ручная правка сцепки на форме | Фильтр выбора + серверная валидация → отказ записи |

## 15. Technical Decisions

### TD-001: Прямые конкретные типы в метаданных CFE
- **Decision:** реквизиты получают `cfg:CatalogRef.Апк*` и др. конкретные типы прямо
  в XML расширения (формат `<v8:Type>cfg:…</v8:Type>`).
- **Why:** решение пользователя (generic-рантайм отменён); Апк* — в основной конфигурации.
- **Trade-off:** жёсткая связь с типовой конфигурацией (при смене АПК — пересборка).
- **Alternatives:** generic+рантайм-разрешение имён (отменено пользователем).

### TD-002: Разрез ТЧ вместо составного реквизита «Модель»
- **Decision:** составной тип «модель техники» реализован парой ТЧ
  (ОсновнаяТехника/Автотранспорт) с однотипными реквизитами, а не одним составным
  реквизитом.
- **Why:** сильнее NFR-001 (НТТ-поля без выбора типа), сильнее FR-002 (тип прицепного
  жёстко задан ТЧ), проще формы.
- **Trade-off:** две почти одинаковые ТЧ (дублирование колонок) — принято (D-008).

### TD-003: Формула и приоритеты коэффициентов
- **Decision:** §6.4, приоритет ручных реквизитов → старт по мощности; К = замена/оригинал;
  смены_замены = смены/К.
- **Why:** утверждено пользователем (D-003); реквизиты существуют (§3 промта, проверено).
- **Trade-off:** без хранения истории коэффициентов (считаются на лету).
- **Alternatives:** регистр коэффициентов (удалён, D-005).

### TD-004: Удаление регистра + сервисной обработки одним коммитом
- **Decision:** §5.5; весь связанные код/права/подсистема/тесты — тем же изменением.
- **Why:** половинчатое состояние (регистр есть, обработчик нет) = рантайм-ошибки.
- **Trade-off:** большой диф; митигация — pre_load_validate + round-trip.

### TD-005: Источники потребности — обороты двух регистров накопления
- **Decision:** АпкМеханизированныеРаботыПоГодовомуПлану +
  АпкТранспортныеРаботыПоГодовомуПлану (Turnovers), отбор по измерениям
  Подразделение/Сценарий/Организация.
- **Why:** канонический ответ rlm-tools-bsl (manager_tables модуля менеджера техкарты;
  парный регистр сведений хранит шапку, техника — только тут).
- **Alternatives:** чтение ТЧ документов техкарт напрямую (медленно, дублирует логику
  проведения).

### TD-006: Значения *_Вер как базовые
- **Decision:** Σ Смен_Вер / Часов_Вер — основной вариант; *_Мин/_Макс не читаем.
- **Why:** «Вер» — вероятностный (с учётом Вероятности) основной план АПК.
- **Trade-off:** если пользователь захочет консервативный (Мин/Макс) — переключатель
  в релиз 2.

### TD-007: Доступность — только проведённые АпкПланТехническихРесурсов
- **Decision:** §6.2; АпкИсторияТранспортныхСредств напрямую НЕ читаем (документ —
  зафиксированный пользователем срез распределения, D-006/§10.3 промта).
- **Trade-off:** без документа распределения доступность = 0 (честно показываем).

### TD-008: Количество = ceil(смен / (дней × сменВдень))
- **Decision:** единицы потребности из смен за период; параметры ДнейПериода/СменВдень
  из формы обработки (паттерн релиза 001: ресурсы ДнейПериода/СменВДень).
- **Why:** простая, объяснимая пользователю арифметика; правится вручную.
- **Alternatives:** учёт сменной нормы выработки модели (реквизит техкарты СменнаяНормаВыработки) — релиз 2 (FAQ Q4).

## 16. Implementation FAQ

**Q1: Почему ТЧ «Оборудование» не автозаполняется?**
Техкарты планируют СХ-оборудование только в сцепке (строка МеханизированныхРабот),
отдельной потребности в нём нет. ТЧ остаётся (D-008) для ручных строк отдельного
оборудования (совместимость с АпкПланТехническихРесурсов.Оборудование) и ретайпируется.

**Q2: Периодичность регистра оборотов — как сопоставить окно расчёта с ПериодНачала/ПериодОкончания строк техкарты?**
Регистр Turnovers имеет измерения ПериодНачала/ПериодОкончания (период работы), запись
оборотного регистра датируется (Период = начало работы). Релиз 1: отбор
`ПериодНачала <= &ПериодПо И ПериодОкончания >= &ПериодС` (работы, пересекающие окно).
Если демо-данные покажут иную семантику периода — уточнить на прогонах сценария 08.

**Q3: Опциональные работы (Опционально=Истина) — включать?**
Да, в *_Вер они уже взвешены Вероятностью типовой логикой АПК. Доп. фильтр не вводим.

**Q4: Учёт СменнаяНормаВыработки (насколько быстро модель выполняет работу)?**
Релиз 1 не использует (смены уже посчитаны техкартой для КОНКРЕТНОЙ модели). При
замещении §6.4 норма меняется через К. Прямой учёт нормы — релиз 2.

**Q5: Что с функциями ИмяСправочникаМоделей(ВидТехники) и рантайм-разрешением?**
Сохраняются (используются Тх_Тесты и enum Тх_ВидыТехники), НО формы/объекты больше
от них не зависят (типы прямые). Рантайм-баг §2.3 закрыт удалением вызывающей формы.

**Q6: Отчёт «Анализ дефицита техники» — меняется ли?**
Только синоним (D-007) и, возможно, заголовки СКД; источники (регистр Тх_ДефицитТехники)
и механика Тх_РасчетДефицита сохраняются, коэффициенты — модельные (§6.4).

**Q7: Privileged/ExternalConnection у новых серверных функций?**
Тх_ТехникаСервер остаётся Privileged=false + ExternalConnection=true (§8 промта:
Privileged=true в CFE запрещён платформой).

**Q8: Может ли пользователь запустить формирование дважды в один документ?**
Да, «Перезаполнить текущий документ» очищает ТЧ и заполняет заново (с подтверждением).

**Q9 (roadmap, вне релиза 1):** предложения замен техникой других подразделений
(расстояния, перемещение своим ходом/тралом, спецразрешения) — зафиксировано в
Out of Scope requirements; каркас — ДоступноЕдиниц по чужим подразделениям не читаем.
