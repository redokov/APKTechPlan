## 1. Маркер тестовой ИБ (Q-006, пункт 1)

Константа CFE `Тх_ТестоваяБаза` (Булево, по умолчанию Ложь). Значение —
данные ИБ: устанавливается ТОЛЬКО в тестовой базе. Установка — скриптами
запуска ПОСЛЕ проверки ссылки на ИБ (инвариант «set only in test infobase»
выполнен конструктивно: скрипт с иной ссылкой до установки не доходит),
идемпотентно (`Установить(Истина)` если Ложь).

`Тх_Тесты.ПроверитьТестовуюБазу()` — первая инструкция каждой из 29
тестовых функций (все — Экспорт = точки входа) и каждого пишущего
хелпера: маркер не установлен → `ВызватьИсключение` с явным текстом
«база не маркирована как тестовая, тестовые записи запрещены». Раннер
обёртками ловит исключение → FAIL — в немаркированной базе весь сьют
падает видимым FAIL-рядом, тихих записей нет.

Пишущие хелперы (граница записи): СоздатьЭлемент, УдалитьСсылку,
ЗаписатьПрипискуТС, УдалитьПрипискуТС, ЗасеятьСтрокиДефицита,
ВосстановитьДефицит, ВосстановитьДефицитПоСценарию,
ЗаписатьПотребностьБезПлана, СоздатьРегистратораТехкарту + новые
функции очистки/реестра. Читающие (НайтиПервыйЭлемент,
СценарийСПотребностью, снимки/контракты) — без маркера: граница —
запись, не чтение. Документы `АпкПланТехническихРесурсов` в тестах
формирования создаются ТОЛЬКО в памяти (записи в БД нет) — проверки
маркера на их создание не требуется, покрыто точкой входа теста.

## 2. Реестр тестовых объектов (пункт 4)

Регистр сведений CFE `Тх_РеестрТестовыхОбъектов`: независимый,
непериодический, без форм; измерение `Объект` — составной тип из
ФАКТИЧЕСКИГО инвентаря фикстур (11 типов, снятых с кода тестов:
9 справочников АпкМодели*/ТранспортныеСредства/АпкСценарииПланирования/
ВидыРаботСотрудников/Организации/СтруктураПредприятия + 2 документа
АпкПланТехническихРесурсов/АпкТехнологическиеКартыНаПоле). «ЛюбаяСсылка»
не используется: синтаксис TypeSet в 8.5-выгрузке не подтверждён
локальным эталоном, составной список — тот же механизм с проверяемым
синтаксисом; новый тип фикстуры = сознательное расширение типа
измерения (задокументировано, не тихое).

Механика:
- СоздатьЭлемент / СоздатьРегистратораТехкарту: успешная запись →
  `ЗарегистрироватьТестовыйОбъект(Ссылка)` (строка реестра).
- УдалитьСсылку: успешное удаление → `СнятьОбъектСРеестра(Ссылка)`;
  НЕудачное → строка остаётся (это и есть сигнал), ЖР Информация —
  только диагностика, НЕ доказательство очистки (пункт 6).
- Регистрационные строки/fixtures приписок/дефицита: строки регистров
  привязаны к регистратору-документу; удаление документа (через
  реестр) убирает и их; строки дефицита чистятся парными
  снимок/восстановление (существующий механизм, ВосстановитьДефицит).
- Раннер `ВыполнитьТесты`: СТАРТ — `УдалитьОстаткиПрошлыхПрогонов()`
  (хвосты упавших прогонов: удалить объекты по строкам реестра,
  очистить строки; неудаляемое остаётся и попадёт в финальную проверку);
  ФИНАЛ — `ОстаткиПослеПрогона()`: строки реестра + неудалённые
  элементы масок → всегда добавляется результат
  `ЧистотаТестовыхДанных` (PASS/FAIL, Провалы = список остатков) —
  EXPECTED_TOTAL 29 → 30, детерминированный счёт.
- Скрипт run_unit_tests_com.py: при FAIL `ЧистотаТестовыхДанных`
  выгружает список остатков в артефакт-файл рядом с логами
  (leftovers_<ts>.txt) — run и так падает от FAIL, артефакт = пункт 4
  «leftover list is written to an artifact file next to the logs».

## 3. Sweep по маскам (пункт 5)

`Тх_Тесты.УбратьОстаткиПоМаскам()`: справочники ТранспортныеСредства +
4 АпкМодели* + АпкСценарииПланирования/ВидыРаботСотрудников/
Организации/СтруктураПредприятия, отбор Наименование ПОДОБНО маски
`Тх_Тест%`, `Тх_VA_%` (маски чек-листа). Удаляет найденное,
возвращает описания неудалённых. Вызов — в стартовой очистке раннера
(вместе с реестром) и в teardown run_va_feature.py (COM). GUID-имён
фикстуры это не трогает (их покрывает реестр) — маски дополняют
реестр для сценариев VA и ручных прогонов.

### 3.1. Коллизия масок со стабильным набором (найдена живым прогоном)

Маска `Тх_Тест%` ловит НЕ только одноразовые остатки: стабильный
набор va_prep_data (фичи 01–09 и тест ТестДоступныеМодели_ПланРаспределения
зависят от него) назван «Тх_Тест Базовая/Аналог/БезМощности/Работа/ТС 001..004».
Первый прогон со sweep (поколение f3cec550) удалил набор → сьют
упал SKIP'ом «нет тестовых ТС (va_prep_data)». Решение: sweep
исключает явный список стабильных имён (`И НЕ Наименование В (&Стабильные)`,
параметр — массив из 8 имён в УбратьОстаткиПоМаскам); набор восстановлен
`scripts/va_prep_data.py` (find-or-create, идемпотентно).

Попутно найден и починен ДОИСТОРИЧЕСКИЙ баг va_prep_data.py: коммит
SRV-02 (9bec7c1) случайно удалил блок выборки base_ref — с тех пор ТС
создавались с АпкМодель = None (тихо пропускалось «if v is not None»).
Оригинальные фикстуры B6 имели модели, поэтому баг не проявлялся, пока
sweep не удалил их и va_prep_data не пересоздал без моделей. Теперь
base_ref берётся из созданной модели (COM-ссылка, не строка), а
update_fields дозаполняет АпкМодель существующим ТС.

### 3.2. Guard'ы раннера (проба маркера)

Стартовая очистка и финальная ОстаткиПослеПрогона обёрнуты Попыткой:
сбой любой из них даёт видимый FAIL-ряд (СтартоваяОчистка FAIL /
ЧистотаТестовыхДанных FAIL с текстом ошибки), а не исключение,
валящее COM-вызов целиком. Принято по пробе: маркер-офф → 31/31 FAIL
(первый — СтартоваяОчистка с текстом маркера), маркер-он → 30/30 PASS
(дополнительная строка не появляется).

### 3.3. Ложный провал теста детерминированности (найден после VA)

После серии сценариев 01–09 тест
ТестДетерминированностьПовторногоРасчета один раз упал на проверке
«значения всех строк идентичны» (повторный прогон — 30/30 PASS).
Причина — дефект самого теста: выгрузка ВыгрузкаДефицита сортировала
по 7 полям, но регистр Тх_ДефицитТехники имеет ещё два измерения —
ИсточникОрганизации и ИсточникПодразделения (строки с разными
источниками — ровно то, что создают сценарии 04/05). При их
отсутствии в УПОРЯДОЧИТЬ две строки с одинаковым префиксом ключа
могут идти в произвольном порядке, а ТаблицыИдентичны сравнивает
по номеру строки → ложный провал. Исправлено: в УПОРЯДОЧИТЬ
добавлены оба измерения (порядок = полный ключ регистра).
Данные годового плана и регистра не пострадали.

## 4. Роли (пункт 3)

Назначение/снятие — только внешний скрипт (как сейчас). Реворк
run_va_feature.py: снапшот исходных Тх-ролей → ensure → прогон →
`finally`: восстановление исходного состояния + `[verify]`; неудачное
восстановление = ВИДИМЫЙ провал прогона (вердикт FAIL с явной
причиной ROLE-RESTORE-FAILED, не «успех с оговоркой»). Override-прогоны
(tc_user) — роли управляются вызывающим (T12), блок не включается.

## 5. Проверка ссылки ИБ в скриптах (пункт 2)

`ALLOWED_IB_REFS = ("dev_erpapk_demo",)` — единый источник в каждом
скрипте запуска: run_unit_tests_com.py, run_va_feature.py,
va_assign_roles_direct.py. До любого подключения/запуска: ссылка ИБ в
строке подключения сверяется с списком, несовпадение — немедленный
выход с явной ошибкой ДО соединения. После проверки (и только тогда) —
идемпотентная установка маркера Тх_ТестоваяБаза.

## 6. Общие данные (пункт 6)

Существующие принципы сохранены: тесты не меняют демо-данные
(фикстуры GUID/маски, удаление только созданного; приписки —
собственные ТС-фикстуры). Новое: неудаление фиксируется строкой
реестра → видимый FAIL прогона; ЖР Информация при неудачной очистке
остаётся диагностикой, доказательством чистоты считается только
пустой реестр + пустой sweep.

## 7. Роли/права CFE

Новые объекты (константа, регистр) используются только под
Администратором (раннер, COM-скрипты); права Тх_Чтение/Тх_Редактирование
не расширяются — VA-сценарии модуль Тх_Тесты не вызывают. Права на
константу/реестр у полноправного администратора есть всегда.

## 8. Вне области

- TEST-03 (вынос раннера в отдельное расширение) — отложено владельцем.
- Реестр НЕ отслеживает строки регистров вне объектов-регистраторов
  (дефицит: парный снимок/восстановление — существующий механизм).
- VA-фикстуры ТХТС* (va_prep_data, 4 предусмотренных ТС) — не sweep-маска.

## 9. Верификация

Статгейты (balance, pre_load (+2 файла), bsl-ls 0 Errors) → загрузка
(канон с граблёй №3: load → РЕСТАРТ АГЕНТА → apply → genid) → юнит
30/30 (29 + ЧистотаТестовыхДанных PASS) → VA 01-09 (finally-восстановление
ролей; после сьюта roles none) → RT v6 (источник +2 файла) → остатки →
книга → коммит. Отдельная проба: временно сбросить маркер → юнит-сьют
падает видимым FAIL-рядом с текстом маркера (и восстановить).

## 10. Граница «разработка / поставка» (требование владельца 2026-11-14)

Вся внешняя обвязка на Python — инструмент ЭТАПА РАЗРАБОТКИ. В поставку
(прод) идут только объекты 1С на встроенном языке: обработки, которые
сами готовят данные и запускают тесты/сценарии. Никаких вызовов Python
из расширения быть не должно.

Фактическое состояние после TEST-02:

| Функция | Где реализовано | Прод-готовность |
|---|---|---|
| Маркер тестовой ИБ | 1С: константа + ПроверитьТестовуюБазу | готово |
| Реестр тестовых объектов | 1С: регистр + хелперы | готово |
| Очистка остатков по маскам | 1С: УбратьОстаткиПоМаскам | готово |
| Итоговый контроль чистоты | 1С: ОстаткиПослеПрогона в раннере | готово |
| Запуск юнит-тестов | 1С: форма раннера (Python — только headless-пуск) | готово |
| Подготовка стабильных фикстур для сценариев | ТОЛЬКО Python (va_prep_data.py) | РАЗРЫВ |
| Запуск сценариев Vanessa | ТОЛЬКО Python (run_va_feature.py) | РАЗРЫВ |
| Снимок/восстановление ролей | ТОЛЬКО Python (va_assign_roles_direct.py) | РАЗРЫВ |

Законно остаются на Python (только разработка): загрузка/выгрузка
расширения, сборка команд конфигуратора, агент, сравнение выгрузок,
проверки баланса и предзагрузочная валидация, headless-пуски прогонов.

Следствие: прод-контур (подготовка данных + запуск Vanessa + роли
внутри 1С) — отдельная задача TEST-04 (§7.3 книги задач); до её
выполнения TEST-02 закрывает только юнит-контур на 1С, а сценарный
контур считается разработческим.
